This is the heart of the formula grammar. `parse_formula` in [parser/mod.rs](/docs/quadratic-core/src/formulas/parser/mod.rs) starts by asking for exactly one `Expression`, and everything a user can write between the `=` and the end of the formula is described here: comparisons, concatenation, arithmetic, ranges, unary signs, percent suffixes, function calls, parentheses and array literals.

Rather than one grammar rule per precedence level, the file has a single parameterised rule, `ExpressionWithPrecedence`, plus an `OpPrecedence` ladder it walks. Each level parses the level above it and then folds any operators of its own around the results — the classic recursive-descent precedence climb, expressed as one rule that recurses into itself with a higher parameter.

## !!steps The precedence ladder

`OpPrecedence` lists the levels from loosest-binding to tightest, and derives `Ord` so levels can be compared directly. `Comparison` is the lowest — `=`, `<`, `>` and friends bind least tightly — and `Atom` is the top, where literals and parenthesised expressions live.

`next()` is the only way to climb, hand-written as a match rather than derived. It deliberately panics at `Atom`: reaching that call would mean the atom level tried to recurse into something above itself. `Default` returns `lowest()`, which is what makes `ExpressionWithPrecedence::default()` mean "a full expression".

```rust ! expression.rs
/// Operator precedence table.
#[derive(Debug, Copy, Clone, PartialEq, Eq, PartialOrd, Ord)]
pub enum OpPrecedence {
    Comparison,
    Concat,
    AddSub,
    MulDiv,
    Pow,
    Range,
    CellRange,
    Prefix,
    Suffix,
    Atom,
}
impl Default for OpPrecedence {
    fn default() -> Self {
        Self::lowest()
    }
}
impl OpPrecedence {
    /// Returns the lowest precedence level.
    pub const fn lowest() -> Self {
        Self::Comparison
    }
    /// Returns the next-highest precedence level. Panics if given
    /// `OpPrecedence::Atom`.
    // !mark
    pub fn next(self) -> Self {
        match self {
            Self::Comparison => Self::Concat,
            Self::Concat => Self::AddSub,
            Self::AddSub => Self::MulDiv,
            Self::MulDiv => Self::Pow,
            Self::Pow => Self::Range,
            Self::Range => Self::CellRange,
            Self::CellRange => Self::Prefix,
            Self::Prefix => Self::Suffix,
            Self::Suffix => Self::Atom,
            Self::Atom => panic!("tried to get operator precedence level beyond {:?}", self),
        }
    }
```

## !!steps Which operators live where

Three lookup methods map a level to the tokens it accepts, and the empty slices are as meaningful as the full ones — they are what the dispatcher later switches on.

Reading down the binary table gives the whole precedence story: comparisons loosest, then `&` for concatenation, then `+` and `-`, then `*` and `/`, then `^`, then `..` and finally `:` for cell ranges. `Prefix` and `Suffix` have no binary operators at all; instead `Prefix` claims `+` and `-` as unary signs, and `Suffix` claims `%`. Note that `+` and `-` appear in two tables — as binary operators at `AddSub` and as unary ones much tighter down at `Prefix`.

```rust ! expression.rs
    /// Returns a list of binary operators at this precedence level.
    pub fn binary_ops(self) -> &'static [Token] {
        use Token::*;
        match self {
            Self::Comparison => &[Eql, Neq, Lt, Gt, Lte, Gte],
            Self::Concat => &[Concat],
            Self::AddSub => &[Plus, Minus],
            Self::MulDiv => &[Mult, Div],
            Self::Pow => &[Power],
            Self::Range => &[RangeOp],
            Self::CellRange => &[CellRangeOp],
            Self::Prefix => &[],
            Self::Suffix => &[],
            Self::Atom => &[],
        }
    }

    /// Returns a list of unary prefix operators at this precedence level.
    pub fn prefix_ops(self) -> &'static [Token] {
        use Token::*;
        match self {
            Self::Prefix => &[Plus, Minus],
            _ => &[],
        }
    }

    /// Returns a list of unary suffix operators at this precedence level.
    pub fn suffix_ops(self) -> &'static [Token] {
        use Token::*;
        match self {
            Self::Suffix => &[Percent],
            _ => &[],
        }
    }
```

## !!steps One public rule, one private one

`Expression` is the only rule other modules use — `parse_formula`, `List` inside `FunctionCall`, `ArrayLiteral` and `ParenExpression` all reference it by name. It carries no precedence of its own and simply forwards both trait methods to `ExpressionWithPrecedence::default()`, i.e. the `Comparison` level.

`ExpressionWithPrecedence` is a private newtype around `OpPrecedence`. Deriving `Default` on it works precisely because `OpPrecedence` has the `Default` impl from the previous step. Both rules display as plain "expression", so error messages never leak the internal precedence level at which parsing failed.

```rust ! expression.rs
/// Matches an expression.
#[derive(Debug, Copy, Clone)]
pub struct Expression;
impl_display!(for Expression, "expression");
impl SyntaxRule for Expression {
    type Output = ast::AstNode;

    fn prefix_matches(&self, p: Parser<'_>) -> bool {
        ExpressionWithPrecedence::default().prefix_matches(p)
    }
    fn consume_match(&self, p: &mut Parser<'_>) -> FormulaResult<Self::Output> {
        // !mark
        p.parse(ExpressionWithPrecedence::default())
    }
}

/// Matches an expression with the given precedence level.
#[derive(Debug, Default, Copy, Clone)]
struct ExpressionWithPrecedence(pub OpPrecedence);
impl_display!(for ExpressionWithPrecedence, "expression");
```

## !!steps Which tokens can start an expression

`prefix_matches` is a full census of the token set. The comment explains the choice: so many tokens could begin an expression that enumerating all of them, with no wildcard arm, is more reliable than trying to be clever. The practical benefit is that adding a token to [lexer.rs](/docs/quadratic-core/src/formulas/lexer.rs) makes this match fail to compile until someone decides which side it belongs on.

The interesting entries are the asymmetries: `Token::LParen` and `Token::LBrace` can open an expression but `Token::LBracket` cannot; closing brackets and separators cannot; comparison operators cannot, but `+` and `-` can, because they double as unary signs. Notice too that `UnterminatedStringLiteral` answers *true* — a half-typed string still looks like an attempt at an expression, so the parser commits and produces a useful error rather than a confusing one.

```rust ! expression.rs
impl SyntaxRule for ExpressionWithPrecedence {
    type Output = ast::AstNode;

    fn prefix_matches(&self, mut p: Parser<'_>) -> bool {
        if let Some(t) = p.next() {
            // There are so many tokens that might match, it's more reliable to
            // just match all of them.
            match t {
                Token::LParen => true,
                Token::LBracket => false,
                Token::LBrace => true,

                Token::RParen | Token::RBracket | Token::RBrace => false,

                Token::ArgSep | Token::RowSep => false,

                Token::Eql | Token::Neq | Token::Lt | Token::Gt | Token::Lte | Token::Gte => false,

                // !mark
                Token::Plus | Token::Minus => true,
                // ...
                Token::Comment | Token::UnterminatedBlockComment => false,

                Token::FunctionCall
                | Token::StringLiteral
                | Token::UnterminatedStringLiteral
                | Token::NumericLiteral
                | Token::CellRef => true,

                Token::Whitespace => false,
                Token::Unknown => false,
            }
        } else {
            false
        }
    }
```

## !!steps Dispatch by level

`consume_match` branches on the level this rule instance carries. `Atom` is the base case: an alternation over the six atomic rules, in order, with `Epsilon` last so that "nothing matched" comes back as `Ok(None)` instead of an error. `.transpose()` flips `FormulaResult` and `Option` around so `unwrap_or_else` can turn that `None` into a single clean "expected expression" error instead of the sprawling list `parse_one_of!` would otherwise produce.

Every other level is chosen by *guard*, asking the lookup tables from earlier which kind of operator lives here: non-empty `binary_ops` means fold binary operators, non-empty `prefix_ops` or `suffix_ops` means fold unary ones. The final arm is `internal_error!` — with the current tables no level reaches it, but a new level added without operators would land there instead of silently misparsing.

```rust ! expression.rs
    fn consume_match(&self, p: &mut Parser<'_>) -> FormulaResult<Self::Output> {
        // Consume an expression at the given precedence level, which may
        // consist of expressions with higher precedence.
        match self.0 {
            OpPrecedence::Atom => parse_one_of!(
                p,
                [
                    FunctionCall.map(Some),
                    StringLiteral.map(Some),
                    NumericLiteral.map(Some),
                    ArrayLiteral.map(Some),
                    CellReference.map(Some),
                    ParenExpression.map(Some),
                    // !mark
                    Epsilon.map(|_| None),
                ],
            )
            .transpose()
            .unwrap_or_else(|| p.expected(self)),

            prec if !prec.binary_ops().is_empty() => parse_binary_ops_expr(p, prec),
            prec if !prec.prefix_ops().is_empty() => parse_prefix_ops(p, prec),
            prec if !prec.suffix_ops().is_empty() => parse_suffix_ops(p, prec),
            prec => internal_error!("don't know what to do for precedence {:?}", prec),
        }
    }
}
```

## !!steps Binary operators, flattened first

The binary case does not build a tree while scanning. It first parses one operand at the *next* level up — that single line is where the precedence climb happens — and then loops as long as the upcoming token is one of this level's operators, pushing each operator and each following operand onto two parallel vectors.

The operator is stored as a `Spanned<String>` holding its literal source text, not as a token; that text later becomes a function name. The comment states the invariant that the folding step relies on: `ops.len()` is always `exprs.len() - 1`. `p.peek_next()` looks ahead without moving the real cursor, so a token that is not one of `allowed_ops` is left untouched for a lower level to consume.

```rust ! expression.rs
/// Parses an expression with any number of binary operators at a specific
/// precedence level.
fn parse_binary_ops_expr(
    p: &mut Parser<'_>,
    precedence: OpPrecedence,
) -> FormulaResult<ast::AstNode> {
    // !mark
    let recursive_expression = ExpressionWithPrecedence(precedence.next());

    let allowed_ops = precedence.binary_ops();

    // First, just make a list of operators and expressions. `ops.len()` should
    // always be equal to `exprs.len() - 1`.
    let mut ops: Vec<Spanned<String>> = vec![];
    let mut exprs: Vec<ast::AstNode> = vec![p.parse(recursive_expression)?];
    while let Some(tok) = p.peek_next() {
        if allowed_ops.contains(&tok) {
            p.next();
            ops.push(Spanned {
                span: p.span(),
                inner: p.token_str().to_string(),
            });
            exprs.push(p.parse(recursive_expression)?);
            continue;
        } else {
            break;
        }
    }
```

## !!steps Folding left or right

Only now does associativity matter, and it is a single branch over `is_right_associative()` — which returns true for exactly one level, `Pow`, so `2^3^2` groups as `2^(3^2)` while `10-3-2` groups as `(10-3)-2`.

Both branches build the same shape from opposite ends: take the extreme operand as the seed, then repeatedly wrap it in an `AstNodeContents::FunctionCall` whose `func` is the operator's source text and whose `args` are the two operands, in source order. That is the key design decision of this parser — there is no dedicated binary-operator AST node; `+` is simply a call to a function named `+`, resolved later against the table in [operators.rs](/docs/quadratic-core/src/formulas/functions/operators.rs). Each new node's span is the merge of its two children, so a nested expression's span always covers its full source text.

```rust ! expression.rs
    let mut ret: ast::AstNode;
    if precedence.is_right_associative() {
        // Take out the last/rightmost expression; that's the deepest AST node.
        ret = exprs.pop().unwrap();
        // Pair up the remaining operators and expressions, and make a new AST
        // node using the previous iteration as the right-hand side of the
        // expression.
        // !mark
        for (lhs, op) in exprs.into_iter().zip(ops).rev() {
            ret = AstNode {
                span: Span::merge(lhs.span, ret.span),
                inner: ast::AstNodeContents::FunctionCall {
                    func: op,
                    args: vec![lhs, ret],
                },
            };
        }
    } else {
        // Take out the first/leftmost expression; that's the deepest AST node.
        let mut exprs_iter = exprs.into_iter();
        ret = exprs_iter.next().unwrap();
        // Pair up the remaining operators and expressions, and make a new AST
        // node using the previous iteration as the left-hand side of the
        // expression.
        // !mark
        for (op, rhs) in ops.into_iter().zip(exprs_iter) {
            ret = AstNode {
                span: Span::merge(ret.span, rhs.span),
                inner: ast::AstNodeContents::FunctionCall {
                    func: op,
                    args: vec![ret, rhs],
                },
            };
        }
    }
    Ok(ret)
}
```

## !!steps Unary signs and the percent suffix

The two unary helpers mirror each other. `parse_prefix_ops` collects every leading `+` or `-` into a vector before parsing the operand, then wraps the operand once per operator; since it iterates the vector in source order and each iteration wraps the previous result, the operator written last ends up outermost. With `+` and `-` as the only prefix operators, the levels here still bind tighter than `^`, which is why the `Prefix` level sits above `Pow` in the ladder.

`parse_suffix_ops` needs no vector: it parses the operand first, then repeatedly consumes a trailing `%` and wraps what it has, which naturally yields left-to-right application. Both produce the same one-argument `FunctionCall` node shape as the binary case, so `-` as a unary operator and `-` as a binary one differ only in argument count.

```rust ! expression.rs
/// Parses an expression with any number of prefix operators.
fn parse_prefix_ops(p: &mut Parser<'_>, precedence: OpPrecedence) -> FormulaResult<ast::AstNode> {
    let allowed_ops = precedence.prefix_ops();
    // ...
    let mut ret = p.parse(ExpressionWithPrecedence(precedence.next()))?;
    // Now pop the operators off the list from right to left.
    for op in ops {
        ret = AstNode {
            span: Span::merge(op.span, ret.span),
            inner: ast::AstNodeContents::FunctionCall {
                func: op,
                args: vec![ret],
            },
        };
    }
    Ok(ret)
}

/// Parses an expression with any number of suffix operators.
fn parse_suffix_ops(p: &mut Parser<'_>, precedence: OpPrecedence) -> FormulaResult<ast::AstNode> {
    let allowed_ops = precedence.suffix_ops();

    // Parse the initial expression.
    let mut ret = p.parse(ExpressionWithPrecedence(precedence.next()))?;

    // Repeatedly try to consume a suffix.
    while let Some(tok) = p.peek_next() {
        if allowed_ops.contains(&tok) {
            p.next();
            let op = Spanned {
                span: p.span(),
                inner: p.token_str().to_string(),
            };
            // ...
        } else {
            break;
        }
    }
    Ok(ret)
}
```

## !!steps Function calls and the rewind trick

The lexer emits a function name together with its opening paren as one `FunctionCall` token, which forces an unusual dance here. The rule consumes that token, strips the trailing `(` to recover the name, and then calls `p.prev()` to step *back* onto the very same token — because the `List` combinator it is about to invoke expects to consume its own `start` delimiter, and that delimiter is this token.

The `List` is configured with `Token::ArgSep` as separator and `Token::RParen` as terminator, with `sep_name` set to "comma" purely for error messages. The result is again an `AstNodeContents::FunctionCall`, identical in shape to what an operator produces — by the time [ast.rs](/docs/quadratic-core/src/formulas/ast.rs) evaluates the tree, `SUM(A1, B1)` and `A1 + B1` are the same kind of node.

```rust ! expression.rs
/// Matches a function call.
#[derive(Debug, Copy, Clone)]
pub struct FunctionCall;
impl_display!(for FunctionCall, "function call");
impl SyntaxRule for FunctionCall {
    type Output = ast::AstNode;

    fn prefix_matches(&self, mut p: Parser<'_>) -> bool {
        p.next() == Some(Token::FunctionCall)
    }
    fn consume_match(&self, p: &mut Parser<'_>) -> FormulaResult<Self::Output> {
        p.parse(Token::FunctionCall)?;
        let Some(func_str) = p.token_str().strip_suffix('(') else {
            internal_error!("function call missing left paren");
        };
        let func = Spanned {
            span: p.span(),
            inner: func_str.to_string(),
        };
        // !mark
        p.prev();

        let spanned_args = p.parse(List {
            inner: Expression,
            sep: Token::ArgSep,
            start: Token::FunctionCall,
            end: Token::RParen,
            sep_name: "comma",
        })?;
        let args = spanned_args.inner;

        Ok(AstNode {
            span: Span::merge(func.span, spanned_args.span),
            inner: ast::AstNodeContents::FunctionCall { func, args },
        })
    }
}
```

## !!steps Parentheses and array literals

`ParenExpression` is three lines of real logic: hand `Surround::paren` an `Expression` mapped into `AstNodeContents::Paren`, and let the combinator from [combinators.rs](/docs/quadratic-core/src/formulas/parser/rules/combinators.rs) do the bracket matching and span merging. Parentheses are kept as an explicit AST node rather than dissolved, so the tree still knows where the user wrote them. Its `impl_display!` even delegates its error text to `Surround::paren(Expression)`.

`ArrayLiteral` parses the brace form the display string spells out — the doubled braces there are format-string escaping. The loop reads one expression at a time and branches on the separator that follows: a comma moves to the next cell in the row, a semicolon starts a new row, a closing brace ends the literal, and anything else produces an error naming all three. A trailing row separator leaves an empty final row, which is popped, and a final `all_equal` check over the row lengths rejects ragged input with `NonRectangularArray`.

```rust ! expression.rs
/// Matches a pair of parentheses containing an expression.
#[derive(Debug, Copy, Clone)]
pub struct ParenExpression;
impl_display!(for ParenExpression, "{}", Surround::paren(Expression));
impl SyntaxRule for ParenExpression {
    type Output = ast::AstNode;

    fn prefix_matches(&self, p: Parser<'_>) -> bool {
        Surround::paren(Expression).prefix_matches(p)
    }
    fn consume_match(&self, p: &mut Parser<'_>) -> FormulaResult<Self::Output> {
        p.parse(Surround::paren(
            Expression.map(|expr| ast::AstNodeContents::Paren(Box::new(expr))),
        ))
    }
}

// ...
/// Matches an array literal.
#[derive(Debug, Copy, Clone)]
pub struct ArrayLiteral;
impl_display!(for ArrayLiteral, "array literal, such as '{{1, 2; 3, 4}}'");
// ...
        let mut rows = vec![vec![]];
        p.parse(Token::LBrace)?;
        loop {
            rows.last_mut().unwrap().push(p.parse(Expression)?);
            // !mark(1:4)
            match p.next() {
                Some(Token::ArgSep) => (),                // next cell within row
                Some(Token::RowSep) => rows.push(vec![]), // start a new row
                Some(Token::RBrace) => break,             // end of array
                // ...
            }
        }
        // ...
        if !rows.iter().map(|row| row.len()).all_equal() {
            return Err(FormulaErrorMsg::NonRectangularArray.with_span(end_span));
        }
```
