This module is the "Lookup functions" category: five functions that turn a
value or a pair of indices into a cell somewhere else. Four of them are pure —
they only walk the array they were handed — and one, `INDIRECT`, actually
reaches back into the grid through the evaluation context.

Like every sibling in this directory, the module exports a `CATEGORY`
constant whose `get_functions` pointer produces the `FormulaFunction` values;
[functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs) merges
all categories into the global `ALL_FUNCTIONS` map that the evaluator consults
by uppercase name.

## !!steps The category, and the one impure function

`CATEGORY` is the registration point: a display name, empty category-level
docs, and the `get_functions` producer. `INDIRECT` is the only entry here that
needs the context, so instead of `util::pure_fn` it builds its `eval` closure
by hand and hands the arguments straight to `ctx.array_mapped_indirect`, which
parses each string as A1 notation relative to the calling cell and fetches it
(see [ctx.rs](/docs/quadratic-core/src/formulas/ctx.rs)). Because it goes
through the array-mapping machinery, an array of reference strings yields an
array of cell values.

```rust ! lookup.rs
use super::*;

pub const CATEGORY: FormulaFunctionCategory = FormulaFunctionCategory {
    include_in_docs: true,
    include_in_completions: true,
    name: "Lookup functions",
    docs: "",
    get_functions,
};

fn get_functions() -> Vec<FormulaFunction> {
    vec![
        FormulaFunction {
            name: "INDIRECT",
            arg_completion: "${1:cellref_string}",
            usages: &["cellref_string"],
            examples: &["INDIRECT(\"Cn7\")", "INDIRECT(\"F\" & B0)"],
            doc: "Returns the value of the cell at a given location.",
            // !mark
            eval: Box::new(|ctx, args| ctx.array_mapped_indirect(args).boxed_local()),
        },
        // ...
    ]
}
```

## !!steps VLOOKUP scans the first column

`VLOOKUP` pulls three required arguments off the iterator with a `let`-`else`
destructure, then accepts — and deliberately ignores — a fourth: the classic
`is_sorted` flag. The comment says it plainly, and the behavior follows: there
is no binary search and no approximate branch, just a linear scan of the first
cell of every row until `values_loosely_equal` says yes.

A fifth argument is a `BadArgumentCount` error, an `output_col` below 1 is
`IndexOutOfBounds`, and a scan that finds nothing produces an `Expected` error
pointing at the search key's span rather than at the whole call.

```rust ! lookup.rs
        FormulaFunction {
            name: "VLOOKUP",
            // ...
            eval: util::pure_fn(|args| {
                let span = args.span;
                let mut a = args.inner.into_iter();
                let (Some(key), Some(table), Some(col)) = (a.next(), a.next(), a.next())
                else {
                    return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
                };
                // !mark
                let _is_sorted = a.next(); // accepted for compatibility; exact match is used
                if a.next().is_some() {
                    return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
                }
                let col = col.to_integer()?;
                if col < 1 {
                    return Err(FormulaErrorMsg::IndexOutOfBounds.with_span(span));
                }
                let rows = table.inner.clone().into_array();
                for row in &rows {
                    if let Some(first) = row.first() {
                        if values_loosely_equal(first, &key.inner) {
                            return row
                                .get(col as usize - 1)
                                .cloned()
                                .ok_or(FormulaErrorMsg::IndexOutOfBounds.with_span(span));
                        }
                    }
                }
                Err(FormulaErrorMsg::Expected {
                    expected: "matching value in first column".into(),
                    got: None,
                }
                .with_span(key.span))
            }),
        },
```

## !!steps HLOOKUP is the same scan, transposed

`HLOOKUP` mirrors `VLOOKUP` argument for argument, including the ignored
sorted flag. The difference is which axis it walks: it takes `rows.first()`
as the header row, scans it for the key, and remembers the *column* index `i`.
The result then comes from the requested output row at that column, so the two
`get` calls are chained the other way around — row first, then element.

An empty table degrades gracefully: `rows.first().cloned().unwrap_or_default()`
yields an empty header row, the loop body never runs, and the function ends in
the same no-match error.

```rust ! lookup.rs
            eval: util::pure_fn(|args| {
                let span = args.span;
                let mut a = args.inner.into_iter();
                let (Some(key), Some(table), Some(out_row)) = (a.next(), a.next(), a.next())
                else {
                    return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
                };
                let _is_sorted = a.next(); // accepted for compatibility; exact match is used
                // ...
                let out_row = out_row.to_integer()?;
                if out_row < 1 {
                    return Err(FormulaErrorMsg::IndexOutOfBounds.with_span(span));
                }
                let rows = table.inner.clone().into_array();
                // !mark
                let first_row = rows.first().cloned().unwrap_or_default();
                for (i, v) in first_row.iter().enumerate() {
                    if values_loosely_equal(v, &key.inner) {
                        return rows
                            .get(out_row as usize - 1)
                            .and_then(|row| row.get(i))
                            .cloned()
                            .ok_or(FormulaErrorMsg::IndexOutOfBounds.with_span(span));
                    }
                }
                Err(FormulaErrorMsg::Expected {
                    expected: "matching value in first row".into(),
                    got: None,
                }
                .with_span(key.span))
            }),
```

## !!steps MATCH flattens first, then branches on mode

`MATCH` is the one function here with real match modes. Before any of that it
normalizes its haystack: an array argument is flattened row-major into a flat
`Vec<Value>`, and a scalar becomes a one-element vector — so position numbers
are indices into that flattened sequence, not row or column coordinates.

`match_mode` defaults to `1` when omitted. Mode `0` is the exact branch: for
every value it accepts either loose equality *or* a wildcard match, with the
search key used as the pattern. Both sides are lowercased first, because
`util::wildcard_match` leaves case handling to its caller.

```rust ! lookup.rs
                let mode = match mode {
                    Some(m) => m.to_number()?,
                    None => 1.0,
                };
                let values: Vec<Value> = match range.inner {
                    // !mark
                    Value::Array(rows) => rows.into_iter().flatten().collect(),
                    v => vec![v],
                };
                let no_match = FormulaErrorMsg::Expected {
                    expected: "matching value in range".into(),
                    got: None,
                }
                .with_span(key.span);

                if mode == 0.0 {
                    let pattern = key.inner.to_string().to_lowercase();
                    for (i, v) in values.iter().enumerate() {
                        if values_loosely_equal(v, &key.inner)
                            // !mark
                            || util::wildcard_match(&pattern, &v.to_string().to_lowercase())
                        {
                            return Ok(Value::Number((i + 1) as f64));
                        }
                    }
                    return Err(no_match);
                }
```

## !!steps Approximate matching without assuming sorted input

The two approximate modes share one loop. `mode > 0` looks for the largest
value at most the target; `mode < 0` looks for the smallest value at least the
target. Rather than trusting the range to be sorted and stopping at the first
crossing, the loop visits every element and keeps a running `best` pair of
index and number — so an unsorted range still gives the right answer, and ties
keep the *earliest* index because `better` requires a strict improvement.

Non-numeric values are skipped by the `let`-`else`, and blank strings are
skipped explicitly even though they coerce to a number. Only the exact branch
compares text; these modes are numeric-only, and the key itself goes through
`to_number` here.

```rust ! lookup.rs
                // approximate modes compare numbers only
                let target = key.to_number()?;
                let mut best: Option<(usize, f64)> = None;
                for (i, v) in values.iter().enumerate() {
                    let Ok(n) = v.to_number() else { continue };
                    // !mark
                    if matches!(v, Value::String(s) if s.trim().is_empty()) {
                        continue;
                    }
                    let candidate = if mode > 0.0 { n <= target } else { n >= target };
                    if candidate {
                        let better = match best {
                            None => true,
                            Some((_, b)) => {
                                if mode > 0.0 {
                                    n > b
                                } else {
                                    n < b
                                }
                            }
                        };
                        if better {
                            best = Some((i, n));
                        }
                    }
                }
                match best {
                    Some((i, _)) => Ok(Value::Number((i + 1) as f64)),
                    None => Err(no_match),
                }
```

## !!steps INDEX is pure indexing

`INDEX` does no searching at all. It takes a range and a 1-based row, with an
optional column defaulting to `1`, and reads straight through
`into_array`. Note the trailing `None` in the destructuring tuple: it is how
the pattern rejects a fourth argument in the same `let`-`else` that binds the
first three.

Both indices must be at least 1, and the `and_then` chain converts any
out-of-range coordinate into `IndexOutOfBounds` instead of panicking.

```rust ! lookup.rs
            eval: util::pure_fn(|args| {
                let span = args.span;
                let mut a = args.inner.into_iter();
                // !mark
                let (Some(range), Some(row), col, None) =
                    (a.next(), a.next(), a.next(), a.next())
                else {
                    return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
                };
                let row = row.to_integer()?;
                let col = match col {
                    Some(c) => c.to_integer()?,
                    None => 1,
                };
                if row < 1 || col < 1 {
                    return Err(FormulaErrorMsg::IndexOutOfBounds.with_span(span));
                }
                range
                    .inner
                    .into_array()
                    .get(row as usize - 1)
                    .and_then(|r| r.get(col as usize - 1))
                    .cloned()
                    .ok_or(FormulaErrorMsg::IndexOutOfBounds.with_span(span))
            }),
```

## !!steps One equality rule for the whole module

Every scan above funnels through `values_loosely_equal`, the module's private
notion of "same value" — documented as matching the equality the `=` operator
uses. If both sides coerce to numbers it compares numbers, so the text `"42"`
finds the number `42`. Otherwise it falls back to an ASCII case-insensitive
string comparison, which is where the "case-insensitive" promise in the
`VLOOKUP` and `HLOOKUP` docs comes from.

The guard in the middle is the subtle part. Numeric comparison is skipped
exactly when `a` is a blank-or-whitespace string and `b` is not, pushing that
pair down to the string comparison instead of letting a blank cell coerce to
zero and match a numeric key.

```rust ! lookup.rs
/// Case-insensitive equality with numeric coercion, matching the equality
/// used by the `=` operator.
fn values_loosely_equal(a: &Value, b: &Value) -> bool {
    if let (Ok(x), Ok(y)) = (a.to_number(), b.to_number()) {
        // !mark(1:3)
        if !matches!(a, Value::String(s) if s.trim().is_empty())
            || matches!(b, Value::String(s) if s.trim().is_empty())
        {
            return x == y;
        }
    }
    a.to_string().eq_ignore_ascii_case(&b.to_string())
}
```

## Implemented functions

| Name | Purpose |
| --- | --- |
| INDIRECT | Returns the value of the cell named by an A1-notation string |
| VLOOKUP | Scans the first column of a range for a key and returns another column of that row |
| HLOOKUP | Scans the first row of a range for a key and returns another row of that column |
| MATCH | Returns the 1-based position of a key in a range, with exact, largest-below, or smallest-above modes |
| INDEX | Returns the value at a 1-based row and column of a range |
