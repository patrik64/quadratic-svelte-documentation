In this engine there is no separate code path for operators. The parser in
[parser/rules/expression.rs](/docs/quadratic-core/src/formulas/parser/rules/expression.rs)
turns every prefix, infix, and suffix operator into a `FunctionCall` node
whose function name is the operator's own source text, and the evaluator in
[ast.rs](/docs/quadratic-core/src/formulas/ast.rs) resolves that name through
the same `lookup_function` it uses for `SUM`. This module is where those names
are defined: `+`, `<=`, `&`, and the rest are entries in the global registry
alongside every other function.

Because they are ordinary registry entries, operators inherit array
broadcasting for free — `A1:A5 * 2` works because the constructors in
[functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs) route
every operator through `ctx.array_map`.

## !!steps A category that hides itself

Every category module exports a `CATEGORY` constant, and this one is the only
category with both visibility flags set to `false`: operators have no
documentation text, no usage strings, and no autocomplete snippets, so they
are excluded from the generated function docs and from editor completions.
They still land in `ALL_FUNCTIONS`, which is all the evaluator needs.

`INTEGER_RANGE_LIMIT` is the guard rail for the range operator further down —
the largest span of integers `..` will materialize into an array.

```rust ! operators.rs
use smallvec::smallvec;

use super::*;

/// Maximum integer range allowed.
// !mark
const INTEGER_RANGE_LIMIT: f64 = 100_000.0;

pub const CATEGORY: FormulaFunctionCategory = FormulaFunctionCategory {
    // !mark(1:2)
    include_in_docs: false,
    include_in_completions: false,
    name: "Operators",
    docs: "",
    get_functions,
};
```

## !!steps Equality is a text comparison

The four equality spellings — Excel's `=` and `<>` plus the C-style `==` and
`!=` — share one helper. `values_eq` does not compare types at all: it
renders both sides with `Display` and compares the resulting text ignoring
ASCII case. Since `Value`'s `Display` writes booleans as `TRUE` and `FALSE`
and numbers through `f64` formatting, `1 = "1"` and `TRUE = "true"` are both
true, while `1 = "1.0"` is false because the strings differ.

The `TODO` records a known gap: a blank cell is an empty string here, and
comparing it against `0` is currently false even though arithmetic treats it
as zero.

```rust ! operators.rs
fn get_functions() -> Vec<FormulaFunction> {
    vec![
        // Comparison operators
        FormulaFunction::operator("=", |[a, b]| Ok(Value::Bool(values_eq(&a, &b)))),
        FormulaFunction::operator("==", |[a, b]| Ok(Value::Bool(values_eq(&a, &b)))),
        FormulaFunction::operator("<>", |[a, b]| Ok(Value::Bool(!values_eq(&a, &b)))),
        FormulaFunction::operator("!=", |[a, b]| Ok(Value::Bool(!values_eq(&a, &b)))),
// ...
fn values_eq(a: &Spanned<Value>, b: &Spanned<Value>) -> bool {
    // TODO: coerce empty cell (but not empty *string*) to zero.
    // !mark
    a.to_string().eq_ignore_ascii_case(&b.to_string())
}
```

## !!steps Ordering is strictly numeric

The four ordering operators take the opposite approach: both sides go through
`to_number`, so the comparison is always between `f64` values. That means
there is no lexicographic ordering of text — comparing two non-numeric
strings produces an `Expected number` error rather than a boolean, and the
`?` propagates it with the offending argument's span attached.

An empty string is the one text value that survives: `Value::to_number` in
[value.rs](/docs/quadratic-core/src/formulas/value.rs) maps it to `0.0`, so a
blank cell compares as zero.

```rust ! operators.rs
        FormulaFunction::operator("<", |[a, b]| {
            // !mark
            Ok(Value::Bool(a.to_number()? < b.to_number()?))
        }),
        FormulaFunction::operator(">", |[a, b]| {
            Ok(Value::Bool(a.to_number()? > b.to_number()?))
        }),
        FormulaFunction::operator("<=", |[a, b]| {
            Ok(Value::Bool(a.to_number()? <= b.to_number()?))
        }),
        FormulaFunction::operator(">=", |[a, b]| {
            Ok(Value::Bool(a.to_number()? >= b.to_number()?))
        }),
```

## !!steps One symbol, two arities

`+` and `-` are the only operators registered with `variadic_operator`,
because each has both a prefix and an infix form: unary `-` negates, binary
`-` subtracts. The two `Some(...)` arms supply the monadic and dyadic
implementations, and the constructor picks between them by argument count at
call time — the parser has already decided which form it produced by building
a one-argument or two-argument call node.

Unary `+` is not a no-op: it still runs `to_number`, so `+"abc"` is an error
and `+"5"` is the number `5`.

```rust ! operators.rs
        // Mathematical operators
        FormulaFunction::variadic_operator(
            "+",
            // !mark(1:2)
            Some(|_ctx, [a]| Ok(Value::Number(a.to_number()?))),
            Some(|_ctx, [a, b]| Ok(Value::Number(a.to_number()? + b.to_number()?))),
        ),
        FormulaFunction::variadic_operator(
            "-",
            Some(|_ctx, [a]| Ok(Value::Number(-a.to_number()?))),
            Some(|_ctx, [a, b]| Ok(Value::Number(a.to_number()? - b.to_number()?))),
        ),
```

## !!steps Division by zero, powers, and percent

Division is the only arithmetic operator that inspects its result at all: the
divisor is evaluated first and a zero divisor returns `DivideByZero` spanned
to the *divisor*, so the editor underlines the `0` rather than the whole
expression. The comment notes this is deliberate parity with the modern
quadratic-core, where `1/0` is an error rather than IEEE infinity.

`^` is plain `f64::powf`. `%` is registered as a one-argument operator — the
parser treats it as a suffix — and simply divides by 100, so `50%` evaluates
to `0.5`.

```rust ! operators.rs
        FormulaFunction::operator("*", |[a, b]| {
            Ok(Value::Number(a.to_number()? * b.to_number()?))
        }),
        FormulaFunction::operator("/", |[a, b]| {
            let divisor = b.to_number()?;
            if divisor == 0.0 {
                // modern-core parity: division by zero is an error, not `inf`
                // !mark
                return Err(FormulaErrorMsg::DivideByZero.with_span(b.span));
            }
            Ok(Value::Number(a.to_number()? / divisor))
        }),
        FormulaFunction::operator("^", |[a, b]| {
            Ok(Value::Number(a.to_number()?.powf(b.to_number()?)))
        }),
        // !mark
        FormulaFunction::operator("%", |[n]| Ok(Value::Number(n.to_number()? / 100.0))),
```

## !!steps The range operator builds a column

`..` is the one operator that manufactures an array. Both endpoints are
rounded to integers by `to_integer`, and the span of the whole expression is
recovered with `Span::merge` so that an oversized range can be reported
against both endpoints at once. Ranges longer than `INTEGER_RANGE_LIMIT` are
rejected with `ArrayTooBig` instead of allocating.

Two details fall out of the construction: the endpoints are sorted, so `5..1`
and `1..5` produce the same ascending values; and each row is a one-element
`smallvec`, which makes the result a single *column* of numbers.

Last comes `&`, the concatenation operator — it uses `Display`, so numbers and
booleans stringify the same way they would in a cell.

```rust ! operators.rs
        FormulaFunction::operator("..", |[a, b]| {
            let span = Span::merge(&a, &b);
            let a = a.to_integer()?;
            let b = b.to_integer()?;
            // !mark(1:3)
            if (a as f64 - b as f64).abs() > INTEGER_RANGE_LIMIT {
                return Err(FormulaErrorMsg::ArrayTooBig.with_span(span));
            }
            Ok(Value::Array(
                if a < b { a..=b } else { b..=a }
                    .map(|i| smallvec![Value::Number(i as f64)])
                    .collect(),
            ))
        }),
        // String operators
        FormulaFunction::operator("&", |[a, b]| {
            Ok(Value::String(a.to_string() + &b.to_string()))
        }),
    ]
}
```

## Implemented functions

| Name | Purpose |
| --- | --- |
| `=` | Equal, comparing both sides as case-insensitive text |
| `==` | Equal; identical behavior to `=` |
| `<>` | Not equal, comparing both sides as case-insensitive text |
| `!=` | Not equal; identical behavior to `<>` |
| `<` | Less than, after coercing both sides to numbers |
| `>` | Greater than, after coercing both sides to numbers |
| `<=` | Less than or equal, after coercing both sides to numbers |
| `>=` | Greater than or equal, after coercing both sides to numbers |
| `+` | Numeric coercion with one argument; addition with two |
| `-` | Negation with one argument; subtraction with two |
| `*` | Multiplication |
| `/` | Division; a zero divisor raises `DivideByZero` |
| `^` | Exponentiation via `powf` |
| `%` | Suffix percent: divides one number by 100 |
| `..` | Ascending column of integers between two endpoints, rejected when they differ by more than 100000 |
| `&` | String concatenation of the two arguments' display forms |

The test module at the bottom of the file pins down two behaviors: operator
precedence and associativity for a mixed expression such as
`1 * -6 + -2 - 1 * -3 ^ 2 ^ 3`, and the treatment of blank cells, where
`C6 + 2` is `2`, `2 * C6` is `0`, and `C6 & "apple" & D6` is `apple`. The
comparison assertions for blank cells are commented out pending a type system
that understands them.

Precedence and the prefix/infix/suffix classification live in
[parser/rules/expression.rs](/docs/quadratic-core/src/formulas/parser/rules/expression.rs);
the tokens themselves come from
[lexer.rs](/docs/quadratic-core/src/formulas/lexer.rs). The `operator` and
`variadic_operator` constructors are in
[functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs), the
coercions in [value.rs](/docs/quadratic-core/src/formulas/value.rs), and the
error variants in
[errors.rs](/docs/quadratic-core/src/formulas/errors.rs). For the comparison
functions users call by name rather than by symbol, see
[logic.rs](/docs/quadratic-core/src/formulas/functions/logic.rs).
