This module is the "Database functions" category — the twelve `D`-prefixed
functions that aggregate records out of a table. Every one of them takes the
same three arguments: a `database` range whose first row holds column headers,
a `field` naming the column to read, and a `criteria` range that repeats
headers in its first row with condition rows below.

Almost all of the module is shared machinery, and only the final aggregation
differs between functions — which is why ten of the twelve are generated by a
single `d_number_fn!` macro. Condition cells are parsed by the same
`Criterion` type that
[statistics.rs](/docs/quadratic-core/src/formulas/functions/statistics.rs)
uses for `COUNTIF` and `SUMIF`, so Excel-style comparison strings and
wildcards behave identically here. Like every sibling in this directory, the
module exposes a `CATEGORY` constant that
[functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs) folds
into the global `ALL_FUNCTIONS` map.

## !!steps Registering the category

`CATEGORY` carries the display name, a one-line blurb for the formula editor,
and the `get_functions` pointer that builds the `FormulaFunction` values.

The two helpers below it set the ground rules. `is_blank` treats any
all-whitespace string as empty — this engine has no distinct blank type, so
that check recurs throughout the file. `to_rows` converts an argument into
rows via `Value::into_array` from
[value.rs](/docs/quadratic-core/src/formulas/value.rs) and rejects ragged
input with `NonRectangularArray`, so the matching code can assume both the
database and the criteria range are rectangles.

```rust ! database.rs
pub const CATEGORY: FormulaFunctionCategory = FormulaFunctionCategory {
    include_in_docs: true,
    include_in_completions: true,
    name: "Database functions",
    docs: "The database and criteria ranges both start with a header row.\n\n",
    get_functions,
};

type Row = SmallVec<[Value; 1]>;

fn is_blank(v: &Value) -> bool {
    matches!(v, Value::String(s) if s.trim().is_empty())
}

fn to_rows(v: Spanned<Value>) -> FormulaResult<Vec<Row>> {
    let span = v.span;
    let rows = v.inner.into_array();
    let width = rows.first().map_or(0, |r| r.len());
    // !mark(1:3)
    if rows.iter().any(|r| r.len() != width) {
        return Err(FormulaErrorMsg::NonRectangularArray.with_span(span));
    }
    Ok(rows)
}
```

## !!steps Selecting the field column

The `field` argument accepts two forms. `field_column` tries a number first: a
1-based column position, validated against the header row's width and
otherwise `IndexOutOfBounds`. If the value is not numeric it falls back to
`header_index`, which matches a header by name after trimming and
lowercasing — so `"sales"` finds a `Sales` column.

A name that matches nothing produces a spanned `Expected` error naming the
offending text, pointed at the `field` argument rather than the whole call.

```rust ! database.rs
fn header_index(headers: &Row, name: &str) -> Option<usize> {
    let lower = name.trim().to_lowercase();
    headers.iter().position(|h| h.to_string().trim().to_lowercase() == lower)
}

/// Resolves `field` (1-based column number or header name) to a column index.
fn field_column(headers: &Row, field: &Spanned<Value>) -> FormulaResult<usize> {
    // !mark(1:7)
    if let Ok(n) = field.inner.to_number() {
        let col = n as i64;
        if col < 1 || col as usize > headers.len() {
            return Err(FormulaErrorMsg::IndexOutOfBounds.with_span(field.span));
        }
        return Ok(col as usize - 1);
    }
    header_index(headers, &field.inner.to_string()).ok_or_else(|| {
        FormulaErrorMsg::Expected {
            expected: "a column header from the database range".into(),
            got: Some(field.inner.to_string().into()),
        }
        .with_span(field.span)
    })
}
```

## !!steps Lining up the criteria columns

`matching_values` is the heart of the module: it returns the field-column
values of every database record that matches. It starts by rectangularizing
both ranges and requiring a header row in each — an empty range is an
`Expected` error, reported at whichever of the two spans is actually missing
its headers.

The interesting preparation is `crit_cols`: each criteria header is resolved
once to a database column index, up front, instead of being looked up again
for every record. The result is an `Option` per criteria column, and a `None`
means that criteria header does not name any database column.

```rust ! database.rs
/// Returns the field-column values of database rows matching the criteria.
fn matching_values(
    database: Spanned<Value>,
    field: &Spanned<Value>,
    criteria: Spanned<Value>,
) -> FormulaResult<Vec<Value>> {
    let db_span = database.span;
    let crit_span = criteria.span;
    let db = to_rows(database)?;
    let crit = to_rows(criteria)?;
    let (Some(headers), Some(crit_headers)) = (db.first(), crit.first()) else {
        return Err(FormulaErrorMsg::Expected {
            expected: "a range with a header row".into(),
            got: None,
        }
        .with_span(if db.is_empty() { db_span } else { crit_span }));
    };
    let col = field_column(headers, field)?;

    // resolve each criteria column to a database column once, and parse the
    // condition cells once
    // !mark(1:4)
    let crit_cols: Vec<Option<usize>> = crit_headers
        .iter()
        .map(|h| header_index(headers, &h.to_string()))
        .collect();
```

## !!steps OR across rows, AND within a row

The matching loop skips the header row of both ranges and encodes the classic
Excel semantics directly in two iterator adapters: `any` over the criteria
rows is the OR, and `all` over the cells of one row is the AND.

Three details soften the rules. A blank condition cell imposes no constraint,
so a half-filled criteria row still works; a criteria column whose header is
not in the database is ignored rather than being an error; and a database row
that is short of that column is tested as an empty string. Finally,
`crit.len() <= 1` — a criteria range consisting of headers only — matches
every record. Each surviving condition is parsed by `Criterion::parse`, which
handles prefixes like `">=10"` and `"<>x"` as well as `*` and `?` wildcards
with `~` escapes.

```rust ! database.rs
    let mut out = Vec::new();
    for row in db.iter().skip(1) {
        // !mark(1:2)
        let matched = crit.iter().skip(1).any(|crit_row| {
            crit_row.iter().enumerate().all(|(i, cond)| {
                if is_blank(cond) {
                    return true;
                }
                let Some(Some(db_col)) = crit_cols.get(i) else {
                    return true; // criteria column not in the database: ignore
                };
                let value = row.get(*db_col).cloned().unwrap_or(Value::String(String::new()));
                Criterion::parse(&cond.to_string()).matches(&value)
            })
        });
        // a criteria range with no condition rows matches everything
        let matched = matched || crit.len() <= 1;
        if matched {
            if let Some(v) = row.get(col) {
                out.push(v.clone());
            }
        }
    }
    Ok(out)
}
```

## !!steps Numbers only, and a fixed argument triple

Most D-functions want numbers, so `matching_numbers` wraps `matching_values`,
drops blanks, and then drops anything that fails `to_number`. That filtering
is what makes `DCOUNT` count *numeric* cells while `DCOUNTA`, which calls
`matching_values` directly, counts non-blank ones.

`d_args` is the shared argument unpacker. Destructuring the iterator as
`(Some, Some, Some, None)` enforces exactly three arguments in a single
pattern; anything else is `BadArgumentCount` at the call's span.

```rust ! database.rs
fn matching_numbers(
    database: Spanned<Value>,
    field: &Spanned<Value>,
    criteria: Spanned<Value>,
) -> FormulaResult<Vec<f64>> {
    Ok(matching_values(database, field, criteria)?
        .iter()
        // !mark(1:2)
        .filter(|v| !is_blank(v))
        .filter_map(|v| v.to_number().ok())
        .collect())
}

/// Unpacks the fixed (database, field, criteria) argument triple.
fn d_args(
    args: Spanned<Vec<Spanned<Value>>>,
) -> FormulaResult<(Spanned<Value>, Spanned<Value>, Spanned<Value>)> {
    let span = args.span;
    let mut a = args.inner.into_iter();
    let (Some(db), Some(field), Some(crit), None) = (a.next(), a.next(), a.next(), a.next())
    else {
        return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
    };
    Ok((db, field, crit))
}
```

## !!steps One macro for ten functions

Every numeric D-function has the same body — unpack three arguments, collect
the matching numbers, reduce — so `d_number_fn!` takes only what differs: the
name, the doc string, one example, and the aggregation. The completion
snippet, usage string, and the whole `eval` closure are boilerplate the macro
supplies.

The `let agg: fn(...) -> FormulaResult = $agg;` binding is what makes the
macro work: it coerces the closure passed in at the call site to a plain
function pointer, so each expansion produces the same non-capturing type that
`util::pure_fn` can leak and reuse. Passing the span into the aggregation lets
a reducer like `DAVERAGE` raise `DivideByZero` pointing at the call.

```rust ! database.rs
/// Builds one D-function over the matched numeric values.
macro_rules! d_number_fn {
    ($name:literal, $doc:literal, $example:literal, $agg:expr) => {
        FormulaFunction {
            name: $name,
            arg_completion: "${1:database}, ${2:field}, ${3:criteria}",
            usages: &["database, field, criteria"],
            examples: &[$example],
            doc: $doc,
            eval: util::pure_fn(|args| {
                let span = args.span;
                let (db, field, crit) = d_args(args)?;
                let values = matching_numbers(db, &field, crit)?;
                // !mark(1:2)
                let agg: fn(Vec<f64>, crate::formulas::Span) -> FormulaResult = $agg;
                agg(values, span)
            }),
        }
    };
}
```

## !!steps The aggregations

With the macro in place, `get_functions` reads as a list of reducers. `DSUM`
is a one-liner; `DAVERAGE` guards the empty case with `DivideByZero`;
`DCOUNT` just reports how many numbers survived filtering. `DMAX` and `DMIN`
fold with `f64::max` and `f64::min` but deliberately return 0 rather than an
infinity when nothing matches, and `DPRODUCT` multiplies.

The four statistical entries share two helpers defined just above
`get_functions`. `sample_variance` divides by `n - 1` and returns `None` for
fewer than two values; `population_variance` divides by `n` and returns `None`
only for an empty list. Each `None` becomes a `DivideByZero` error, and the
`DSTDEV` and `DSTDEVP` variants take the square root of the same result.

```rust ! database.rs
        d_number_fn!(
            "DSUM",
            "Adds the numbers in the field column of database records that match the criteria.",
            "DSUM(A0:C10, \"Sales\", E0:F1)",
            |v, _span| Ok(Value::Number(v.iter().sum()))
        ),
        d_number_fn!(
            "DAVERAGE",
            "Averages the numbers in the field column of database records that match the criteria.",
            "DAVERAGE(A0:C10, \"Sales\", E0:F1)",
            |v, span| {
                if v.is_empty() {
                    return Err(FormulaErrorMsg::DivideByZero.with_span(span));
                }
                Ok(Value::Number(v.iter().sum::<f64>() / v.len() as f64))
            }
        ),
        // ...
        d_number_fn!(
            "DSTDEV",
            "Estimates the standard deviation of a population sample from the matching records.",
            "DSTDEV(A0:C10, \"Sales\", E0:F1)",
            // !mark(1:3)
            |v, span| sample_variance(&v)
                .map(|var| Value::Number(var.sqrt()))
                .ok_or_else(|| FormulaErrorMsg::DivideByZero.with_span(span))
        ),
```

## !!steps The two functions the macro cannot make

`DCOUNTA` and `DGET` are written out in full because neither reduces a list of
numbers. `DCOUNTA` counts the matching cells that are not blank, keeping text
and booleans that `matching_numbers` would have discarded.

`DGET` is the strict one: it demands exactly one matching record. Zero matches
and several matches are both errors — the same `Expected` variant, with the
`got` field reporting either `"none"` or the number of records that matched —
so a formula that silently returns the first of many is not possible here.

```rust ! database.rs
        FormulaFunction {
            name: "DCOUNTA",
            arg_completion: "${1:database}, ${2:field}, ${3:criteria}",
            usages: &["database, field, criteria"],
            examples: &["DCOUNTA(A0:C10, \"Name\", E0:F1)"],
            doc: "Counts the non-blank cells in the field column of database \
                  records that match the criteria.",
            eval: util::pure_fn(|args| {
                let (db, field, crit) = d_args(args)?;
                let values = matching_values(db, &field, crit)?;
                Ok(Value::Number(values.iter().filter(|v| !is_blank(v)).count() as f64))
            }),
        },
        // ...
            eval: util::pure_fn(|args| {
                let span = args.span;
                let (db, field, crit) = d_args(args)?;
                let mut values = matching_values(db, &field, crit)?;
                match values.len() {
                    // !mark(1:2)
                    1 => Ok(values.remove(0)),
                    0 => Err(FormulaErrorMsg::Expected {
                        expected: "exactly one matching record".into(),
                        got: Some("none".into()),
                    }
                    .with_span(span)),
                    n => Err(FormulaErrorMsg::Expected {
                        expected: "exactly one matching record".into(),
                        got: Some(n.to_string().into()),
                    }
                    .with_span(span)),
                }
            }),
```

## Implemented functions

| Name | Purpose |
| --- | --- |
| DSUM | Adds the numbers in the field column of matching records |
| DAVERAGE | Averages the numbers in the field column of matching records; errors when none match |
| DCOUNT | Counts the numeric cells in the field column of matching records |
| DMAX | Largest number in the field column of matching records, or 0 when none match |
| DMIN | Smallest number in the field column of matching records, or 0 when none match |
| DPRODUCT | Multiplies the numbers in the field column of matching records |
| DSTDEV | Sample standard deviation of the matching numbers, using an `n - 1` denominator |
| DSTDEVP | Population standard deviation of the matching numbers |
| DVAR | Sample variance of the matching numbers, using an `n - 1` denominator |
| DVARP | Population variance of the matching numbers |
| DCOUNTA | Counts the non-blank cells in the field column of matching records |
| DGET | Returns the single matching record's field value; errors on zero or multiple matches |
