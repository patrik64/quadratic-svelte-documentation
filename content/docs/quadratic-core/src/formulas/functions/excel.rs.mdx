This module implements no spreadsheet functions at all. It is a data file with
one accessor: a set of 522 Excel function names, consulted only when a formula
calls something the engine does not have. Typing `=BESSELI(1, 0)` then gets
"BESSELI is a valid Excel function, but is not implemented in this version"
instead of the blunt "There is no function with this name".

That makes it the odd sibling in this directory: every other module exports a
`CATEGORY` for the registry in
[functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs), while
this one exports a plain predicate. It is also the only submodule declared
`pub mod`, because its caller — the evaluator in
[ast.rs](/docs/quadratic-core/src/formulas/ast.rs) — lives outside the
`functions` module.

## !!steps A better error message, nothing more

The header comment states the contract precisely, including the maintenance
consequence: implemented functions are resolved first by `lookup_function`, so
this list is reached only on a miss and never needs pruning when a function
graduates from "known name" to "actually implemented". A name may appear here
and be implemented at the same time with no ill effect.

The consumer is the function-call arm of the evaluator: when
`functions::lookup_function` returns `None`, it asks this predicate whether
the name is at least a real Excel name, and picks between
`UnimplementedExcelFunction(name)` and `BadFunctionName` accordingly — both
defined in [errors.rs](/docs/quadratic-core/src/formulas/errors.rs).

```rust ! excel.rs
//! Allowlist of known Excel function names, from the modern core, used to
//! turn "no function with this name" into a friendlier "valid Excel
//! function, but not implemented here" for names we recognize. Implemented
//! functions win first in `lookup_function`, so this is only consulted on a
//! miss and never needs pruning.

use std::collections::HashSet;

use lazy_static::lazy_static;

// !mark
pub fn is_valid_excel_function(name: &str) -> bool {
    ALL_EXCEL_FUNCTIONS.contains(name.to_ascii_uppercase().as_str())
}
```

## !!steps A const slice, hashed once on demand

The names live in a `const` slice of string literals, but lookups go through a
`HashSet` built by `lazy_static` the first time anything touches it — the same
lazy-initialization pattern `ALL_FUNCTIONS` uses in
[functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs). The
set borrows the literals rather than owning strings, so the whole structure is
522 pointers into static memory.

The query is uppercased with `to_ascii_uppercase` before the lookup, matching
how `lookup_function` normalizes names, so `=besseli(...)` reports the same
friendly error as `=BESSELI(...)`. Only the ASCII variant is used, which is
also all the stored names need.

```rust ! excel.rs
pub fn is_valid_excel_function(name: &str) -> bool {
    // !mark
    ALL_EXCEL_FUNCTIONS.contains(name.to_ascii_uppercase().as_str())
}

lazy_static! {
    // !mark
    static ref ALL_EXCEL_FUNCTIONS: HashSet<&'static str> =
        EXCEL_FUNCTIONS_LIST.iter().cloned().collect();
}

const EXCEL_FUNCTIONS_LIST: &[&str] = &[
    "ABS",
    "ACCRINT",
    "ACCRINTM",
    "ACOS",
    "ACOSH",
```

## !!steps Roughly alphabetical, and that is fine

The list reads as alphabetical, but it is not sorted: `AGGREGATE` sits before
`ADDRESS` here, and there are about two dozen similar slips further down
(`TANH` before `TAKE`, `ISTEXT` before `ISO.CEILING`). Nothing depends on the
order — membership is answered by the hash set — so the ordering is purely a
convenience for humans reading or editing the file.

The `A` block also shows what the list is *not*: it carries `ACOT` and
`ACOTH`, which the engine implements, right next to `AMORDEGRC` and
`ARABIC`, which it does not. Names are recorded without any hint of which
side of that line they fall on.

## !!steps Both spellings of the statistical functions

Seventy-one of the 522 entries contain a dot. Modern Excel renamed most of its
statistical functions into dotted families — `NORM.DIST`, `NORM.INV`,
`NORM.S.DIST` — while keeping the pre-2010 spellings working, and the list
keeps both so that a formula written against either generation gets the
"not implemented in this version" message rather than "no function with this
name".

This matters because the engine's own parser has no special handling for dots
in function names; a name like `NORM.S.INV` is only ever going to be matched
as a whole string, here or in the registry.

```rust ! excel.rs
    "NETWORKDAYS",
    "NETWORKDAYS.INTL",
    "NOMINAL",
    // !mark(1:8)
    "NORM.DIST",
    "NORMDIST",
    "NORMINV",
    "NORM.INV",
    "NORM.S.DIST",
    "NORMSDIST",
    "NORM.S.INV",
    "NORMSINV",
    "NOT",
    "NOW",
    "NPER",
    "NPV",
    "NUMBERVALUE",
```

## !!steps Modern additions the engine has no answer for

The comment at the top of the file says the list came "from the modern core",
and the `L`–`M` stretch shows what that means: `LAMBDA`, `LET`, `MAKEARRAY`,
and `MAP` are recent additions to Excel, none of which this formula engine
implements — its AST in
[ast.rs](/docs/quadratic-core/src/formulas/ast.rs) has no node for a function
value, only literals, cell references, arrays, and calls by name. Listing them
costs one line each and converts a dead-end error into an informative one.

`LOOKUP` is in the same stretch and is likewise unimplemented, while its
neighbors `MATCH` and `LEN` do resolve (see
[lookup.rs](/docs/quadratic-core/src/formulas/functions/lookup.rs) and
[string.rs](/docs/quadratic-core/src/formulas/functions/string.rs)) — another
reminder that presence here says nothing either way.

## !!steps The tail end

The file simply stops after `ZTEST`; there is no trailing logic, no test
module, and no export beyond the predicate at the top. The last stretch is
worth a look anyway because it is dense with the dynamic-array and lookup
functions users reach for most: `XLOOKUP`, `XMATCH`, `VSTACK`, `WRAPROWS`,
alongside the financial `XIRR` and `XNPV` that
[financial.rs](/docs/quadratic-core/src/formulas/functions/financial.rs) does
implement.

Adding a newly recognized name is a one-line change here; making it actually
work means adding a `FormulaFunction` to one of the category modules, after
which this entry quietly stops being consulted for that name.

## Implemented functions

This module declares no spreadsheet functions — it stores names, with no
semantics attached to any of them, so there is nothing here to give a
per-function behavior. The complete set of items it defines is:

| Name | Purpose |
| --- | --- |
| is_valid_excel_function | Returns whether a name, uppercased, is in the allowlist |
| ALL_EXCEL_FUNCTIONS | Lazily built `HashSet` of the names, used for membership tests |
| EXCEL_FUNCTIONS_LIST | The `const` slice holding all 522 recognized Excel function names |

The predicate's only caller is the function-call evaluator in
[ast.rs](/docs/quadratic-core/src/formulas/ast.rs); the two error variants it
chooses between are in
[errors.rs](/docs/quadratic-core/src/formulas/errors.rs); and the registry
whose miss triggers the whole path is
[functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs). The
categories that determine which of these 522 names actually resolve include
[mathematics.rs](/docs/quadratic-core/src/formulas/functions/mathematics.rs),
[statistics.rs](/docs/quadratic-core/src/formulas/functions/statistics.rs),
[datetime.rs](/docs/quadratic-core/src/formulas/functions/datetime.rs), and
[financial.rs](/docs/quadratic-core/src/formulas/functions/financial.rs).
