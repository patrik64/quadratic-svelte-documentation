This module is the "Mathematics functions" category of the formula engine.
Most of its eighteen functions are thin wrappers over `f64` methods, so the
interesting code is in the three shared helpers at the top of the file: a
rounding-mode enum used by `ROUND`, `ROUNDUP`, and `ROUNDDOWN`, and an
increment-rounding helper shared by `CEILING` and `FLOOR`.

Like every sibling in this directory, the module exports a `CATEGORY` constant
whose `get_functions` pointer produces the actual `FormulaFunction` values;
[functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs) collects
all categories into the global `ALL_FUNCTIONS` map that the evaluator looks up
by uppercase name.

## !!steps One category, eighteen functions

The `CATEGORY` constant registers the module: a display name, category-level
docs for the formula editor (empty here), and a `get_functions` pointer
returning `Vec<FormulaFunction>`.

`SUM` and `PRODUCT` are the two aggregate functions, and both delegate to
helpers in [util.rs](/docs/quadratic-core/src/formulas/functions/util.rs) that
flatten every argument — ranges included — into a stream of numbers, silently
skipping values that are not numeric. That is why `SUM("", "abc", 12)` is 12
rather than an error. An empty argument list gives the identity of each
operation: `0` for `SUM`, `1` for `PRODUCT`.

```rust ! mathematics.rs
pub const CATEGORY: FormulaFunctionCategory = FormulaFunctionCategory {
    include_in_docs: true,
    include_in_completions: true,
    name: "Mathematics functions",
    docs: "",
    get_functions,
};

// ...

fn get_functions() -> Vec<FormulaFunction> {
    vec![
        FormulaFunction {
            name: "SUM",
            arg_completion: "${1:a, b, ...}",
            usages: &["a, b, ..."],
            examples: &["SUM(B2:C6, 15, E1)"],
            doc: "Adds all values.\nReturns `0` if given no values.",
            // !mark
            eval: util::pure_fn(|args| Ok(Value::Number(util::sum(&args.inner)))),
        },
        FormulaFunction {
            name: "PRODUCT",
            arg_completion: "${1:a, b, ...}",
            usages: &["a, b, ..."],
            examples: &["PRODUCT(B2:C6, 0.002, E1)"],
            doc: "Multiplies all values.\nReturns 1 if given no values.",
            // !mark
            eval: util::pure_fn(|args| Ok(Value::Number(util::product(&args.inner)))),
        },
        // ...
    ]
}
```

## !!steps Fixed-arity functions are one-liners

Where an aggregate uses `util::pure_fn` and inspects the whole argument list,
a fixed-arity function uses `util::array_mapped`, which destructures the
arguments into an array of exactly `N` values. The arity is therefore checked
by the framework, not by the function body — calling `ABS()` or
`ABS(16, 17)` fails with `BadArgumentCount` before this closure ever runs.

`array_mapped` also broadcasts: passing a range to `SQRT` evaluates the
closure once per cell and returns an array. `ABS`, `SQRT`, `POWER`, `EXP`,
`LN`, `LOG10`, and `INT` all follow this pattern, each forwarding to the
matching `f64` method after `to_number` coerces the argument.

```rust ! mathematics.rs
        FormulaFunction {
            name: "ABS",
            arg_completion: "${1:number}",
            usages: &["number"],
            examples: &["ABS(-4)"],
            doc: "Returns the absolute value of a number.",
            // !mark
            eval: util::array_mapped(|[number]| Ok(Value::Number(number.to_number()?.abs()))),
        },
        FormulaFunction {
            name: "SQRT",
            arg_completion: "${1:number}",
            usages: &["number"],
            examples: &["SQRT(2)"],
            doc: "Returns the square root of a number.",
            eval: util::array_mapped(|[number]| Ok(Value::Number(number.to_number()?.sqrt()))),
        },
        FormulaFunction {
            name: "POWER",
            arg_completion: "${1:base}, ${2:exponent}",
            usages: &["base, exponent"],
            examples: &["POWER(2, 10)"],
            doc: "Returns `base` raised to the power of `exponent`.",
            eval: util::array_mapped(|[base, exponent]| {
                Ok(Value::Number(base.to_number()?.powf(exponent.to_number()?)))
            }),
        },
```

## !!steps An optional second argument means manual arity checks

`LOG` accepts either one or two arguments, so it cannot use `array_mapped`'s
fixed arity. The pattern used throughout this file appears here in full: take
an iterator over the arguments, `let`-else on the first (a missing first
argument is `BadArgumentCount`), let the second stay an `Option`, and then
reject a third with `a.next().is_some()`.

The base defaults to 10 when omitted, and a base of zero or less is rejected
with `BadNumber` rather than being handed to `f64::log`, which would return
a NaN or an infinity. Note that the error is spanned to the whole call, not
to the base argument.

```rust ! mathematics.rs
            doc: "Returns the logarithm of a number. Uses base 10 unless a base is given.",
            eval: util::pure_fn(|args| {
                let span = args.span;
                let mut a = args.inner.into_iter();
                // !mark
                let (Some(number), base) = (a.next(), a.next()) else {
                    return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
                };
                if a.next().is_some() {
                    return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
                }
                let base = match base {
                    Some(b) => b.to_number()?,
                    None => 10.0,
                };
                // !mark
                if base <= 0.0 {
                    return Err(FormulaErrorMsg::BadNumber.with_span(span));
                }
                Ok(Value::Number(number.to_number()?.log(base)))
            }),
```

## !!steps Three rounding modes, one implementation

`ROUND`, `ROUNDUP`, and `ROUNDDOWN` differ only in which way a tie or a
fraction goes, so they share `round_fn` and pass a `RoundMode`. The
digit-count argument goes through `to_integer`, which itself rounds, and
becomes a power-of-ten scale factor: multiply, round, divide back. A negative
digit count therefore rounds to tens, hundreds, and so on, because the factor
is less than 1.

The three modes map onto three `f64` methods. `Nearest` is `f64::round`, which
breaks ties away from zero. `AwayFromZero` has to branch on the sign — `ceil`
for positives, `floor` for negatives — since neither method alone means "away
from zero". `TowardZero` is exactly `trunc`.

```rust ! mathematics.rs
#[derive(Copy, Clone)]
enum RoundMode {
    Nearest,
    AwayFromZero,
    TowardZero,
}

/// Shared implementation for ROUND/ROUNDUP/ROUNDDOWN: 1 or 2 arguments.
fn round_fn(args: Spanned<Vec<Spanned<Value>>>, mode: RoundMode) -> FormulaResult {
    let span = args.span;
    let mut a = args.inner.into_iter();
    let (Some(number), digits) = (a.next(), a.next()) else {
        return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
    };
    if a.next().is_some() {
        return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
    }
    let digits = match digits {
        Some(d) => d.to_integer()?,
        None => 0,
    };
    // !mark(1:2)
    let factor = 10.0_f64.powi(digits as i32);
    let x = number.to_number()? * factor;
    let rounded = match mode {
        RoundMode::Nearest => x.round(),
        RoundMode::AwayFromZero => {
            if x >= 0.0 {
                x.ceil()
            } else {
                x.floor()
            }
        }
        RoundMode::TowardZero => x.trunc(),
    };
    Ok(Value::Number(rounded / factor))
}
```

## !!steps CEILING and FLOOR round to a multiple

`CEILING` and `FLOOR` snap to a multiple of an increment rather than to a
number of decimal places, and they share `increment_round`. The only
difference between them is the `fn(f64) -> f64` passed in: `f64::ceil` or
`f64::floor`, applied to the value divided by the increment before
multiplying back.

The increment defaults to 1, which makes bare `CEILING(8.1)` and
`FLOOR(8.9)` behave like ordinary ceiling and floor. A zero increment would
divide by zero, so it short-circuits to `0` — the comment records that this
matches the behavior of the modern quadratic-core rather than being an
accident.

```rust ! mathematics.rs
/// Shared implementation for CEILING/FLOOR: `(number)` or `(number, increment)`.
/// Matches the modern core: a zero increment yields 0.
fn increment_round(args: Spanned<Vec<Spanned<Value>>>, round: fn(f64) -> f64) -> FormulaResult {
    let span = args.span;
    let mut a = args.inner.into_iter();
    let (Some(number), increment) = (a.next(), a.next()) else {
        return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
    };
    if a.next().is_some() {
        return Err(FormulaErrorMsg::BadArgumentCount.with_span(span));
    }
    let increment = match increment {
        Some(i) => i.to_number()?,
        None => 1.0,
    };
    // !mark
    if increment == 0.0 {
        return Ok(Value::Number(0.0));
    }
    let n = number.to_number()?;
    // !mark
    Ok(Value::Number(round(n / increment) * increment))
}
```

## !!steps MOD follows the sign of the divisor

Rust's `%` on floats is a *remainder*: it keeps the sign of the dividend, so
`-7 % 3` is `-1`. Spreadsheets expect a *modulo* whose result takes the sign
of the divisor, making `MOD(-7, 3)` equal `2`. The double-remainder
expression `((n % d) + d) % d` converts one into the other — adding `d` lifts
a negative remainder into range, and the second `%` brings values back down
when the first remainder was already non-negative.

A zero divisor is caught up front and reported as `DivideByZero`, spanned to
the divisor argument so the editor underlines the offending expression.

```rust ! mathematics.rs
            doc: "Returns the remainder after dividing `number` by `divisor`. \
                  The result has the same sign as `divisor`.",
            eval: util::array_mapped(|[number, divisor]| {
                let d = divisor.to_number()?;
                // !mark
                if d == 0.0 {
                    return Err(FormulaErrorMsg::DivideByZero.with_span(divisor.span));
                }
                let n = number.to_number()?;
                // !mark
                Ok(Value::Number(((n % d) + d) % d))
            }),
        },
```

## !!steps Constants are zero-argument functions

`PI` and `TAU` are still `FormulaFunction` values, not parser-level literals,
which is why they are written with parentheses in a formula. `util::constant_fn`
builds an `eval` that verifies the argument list is empty — `PI(16)` is a
`BadArgumentCount` error — and otherwise clones the stored value.

`std::f64::consts::TAU` is 2π, so `TAU()` starts with `6.283`; the
trigonometric functions that consume these constants live in
[trigonometry.rs](/docs/quadratic-core/src/formulas/functions/trigonometry.rs).

```rust ! mathematics.rs
        // Constants
        FormulaFunction {
            name: "PI",
            arg_completion: "",
            usages: &[""],
            examples: &["PI()"],
            doc: "Returns π, the circle constant.",
            // !mark
            eval: util::constant_fn(Value::Number(std::f64::consts::PI)),
        },
        FormulaFunction {
            name: "TAU",
            arg_completion: "",
            usages: &[""],
            examples: &["TAU()"],
            doc: "Returns τ, the circle constant equal to 2π.",
            // !mark
            eval: util::constant_fn(Value::Number(std::f64::consts::TAU)),
        },
    ]
}
```
