This module is the "Financial functions" category of the formula engine:
payments and rates (`PMT`, `FV`, `PV`, `NPER`, `RATE`), loan amortization
(`IPMT`, `PPMT`, `CUMIPMT`, `CUMPRINC`), depreciation (`SLN`, `SYD`, `DB`,
`DDB`, `VDB`), and cash-flow analysis (`NPV`, `IRR`, `MIRR`, `XNPV`, `XIRR`).
Its header notes that these were backported from the modern quadratic-core's
`financial/loan.rs` and `financial/investment.rs`, and that the
bond, securities, and treasury families remain unported.

Like every sibling in this directory, the module exports a `CATEGORY`
constant whose `get_functions` pointer produces the actual `FormulaFunction`
values; [functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs)
flattens all categories into the global `ALL_FUNCTIONS` map that the evaluator
looks up by uppercase name. Everything below is built from a handful of shared
private helpers rather than one closure per formula.

## !!steps One category, twenty-one functions

The `CATEGORY` constant is the registration point: a display name, a docs
blurb for the formula editor — here the sign convention, cash outflows
negative and inflows positive — and the `get_functions` pointer. Each entry
in the returned vector is a `FormulaFunction` bundling name, autocomplete
snippet, usage strings, examples, docs, and an `eval` closure.

`PMT` shows the shape every function in this file follows: `util::pure_fn`
wraps a closure over the raw argument list, `Args::new` checks the arity,
optional arguments fall back to defaults, and the actual arithmetic lives in
a shared free function.

```rust ! financial.rs
pub const CATEGORY: FormulaFunctionCategory = FormulaFunctionCategory {
    include_in_docs: true,
    include_in_completions: true,
    name: "Financial functions",
    docs: "Cash outflows are negative, inflows positive, as in Excel.\n\n",
    get_functions,
};

// ...
```

## !!steps Time value of money in three helpers

`calculate_pmt`, `calculate_fv`, and `calculate_pv` are the same equation
solved for three different unknowns, and `PMT`, `FV`, and `PV` are barely more
than argument shuffling on top of them. Two quantities recur: `pvif`, the
compounding factor `(1 + rate)^nper`, and `fvifa`, the annuity factor
`(pvif - 1) / rate`.

Each helper special-cases a zero rate, because both factors degenerate there —
with no interest, the payments simply divide the principal evenly across the
periods. Signs follow the Excel convention: the results are negated so that a
loan taken as a positive present value produces a negative payment.

```rust ! financial.rs
fn calculate_pmt(rate: f64, nper: f64, pv: f64, fv: f64, payment_type: f64) -> f64 {
    // !mark
    if rate == 0.0 {
        -(pv + fv) / nper
    } else {
        let pvif = (1.0 + rate).powf(nper);
        let pmt = rate * (pv * pvif + fv) / (pvif - 1.0);
        -pmt / (1.0 + rate * payment_type)
    }
}

fn calculate_fv(rate: f64, nper: f64, pmt: f64, pv: f64, payment_type: f64) -> f64 {
    if rate == 0.0 {
        -(pv + pmt * nper)
    } else {
        let pvif = (1.0 + rate).powf(nper);
        let fvifa = (pvif - 1.0) / rate;
        -pv * pvif - pmt * (1.0 + rate * payment_type) * fvifa
    }
}

fn calculate_pv(rate: f64, nper: f64, pmt: f64, fv: f64, payment_type: f64) -> f64 {
    if rate == 0.0 {
        -(fv + pmt * nper)
    } else {
        let pvif = (1.0 + rate).powf(nper);
        let fvifa = (pvif - 1.0) / rate;
        (-fv - pmt * (1.0 + rate * payment_type) * fvifa) / pvif
    }
}
```

## !!steps Payment timing, and NPER in closed form

The optional `type` argument selects when payments fall due.
`normalize_payment_type` collapses it to exactly `0.0` or `1.0`: anything
non-zero (and any missing argument defaults to zero) means an annuity due,
payments at the start of each period. Everywhere else in the file that value
appears as the factor `1 + rate * t`, which advances one period of interest
onto every payment.

`NPER` is the one member of the family that does not call a shared helper: it
inverts the annuity equation analytically. A zero rate reduces to a plain
division — guarded against a zero payment — and otherwise the period count is
a ratio of logarithms. Because the logarithm's argument can go non-positive
for inputs that never amortize, the code rejects that case rather than
returning a NaN.

```rust ! financial.rs
fn normalize_payment_type(payment_type: Option<f64>) -> f64 {
    if payment_type.unwrap_or(0.0) != 0.0 { 1.0 } else { 0.0 }
}

// ...

            eval: util::pure_fn(|args| {
                let a = Args::new(args, 3, 5)?;
                let (rate, pmt, pv) = (a.num(0)?, a.num(1)?, a.num(2)?);
                let fv = a.opt_num(3)?.unwrap_or(0.0);
                let t = normalize_payment_type(a.opt_num(4)?);
                if rate == 0.0 {
                    if pmt == 0.0 {
                        return Err(FormulaErrorMsg::DivideByZero.with_span(a.span));
                    }
                    return Ok(Value::Number(-(pv + fv) / pmt));
                }
                let pmt_factor = 1.0 + rate * t;
                let log_arg = (pmt * pmt_factor - fv * rate) / (pmt * pmt_factor + pv * rate);
                // !mark(1:3)
                if log_arg <= 0.0 {
                    return Err(a.invalid());
                }
                Ok(Value::Number(log_arg.ln() / (1.0 + rate).ln()))
            }),
```

## !!steps The amortization walk

There is no closed form here: `balance_before` simply replays the loan period
by period, adding interest and applying the standard payment, and returns the
balance entering period `per`. For an annuity due it adds the payment before
charging interest and takes it back off afterwards, so the period's interest
is computed on the reduced balance. `IPMT`, `PPMT`, `CUMIPMT`, and `CUMPRINC`
all share this walk, which makes them linear in the period index.

`IPMT` recomputes the standard payment, replays the balance, and returns the
negated interest on it. The annuity-due edge case is explicit: when payments
are due at the start and the period is the first one, no interest has accrued
yet, so the answer is exactly zero. `PPMT` calls the same code and returns
`pmt - ipmt`, which is why interest and principal always sum back to the
payment.

```rust ! financial.rs
/// Amortization walk shared by IPMT/PPMT/CUMIPMT/CUMPRINC: returns the
/// balance entering `per` given the standard payment.
fn balance_before(rate: f64, pv: f64, pmt: f64, payment_type: f64, per: i64) -> f64 {
    let mut balance = pv;
    for _ in 1..per {
        // !mark(1:3)
        if payment_type == 1.0 {
            balance += pmt;
        }
        let interest = balance * rate;
        balance = balance + interest + pmt;
        if payment_type == 1.0 {
            balance -= pmt;
        }
    }
    balance
}

// ...

            eval: util::pure_fn(|args| {
                let a = Args::new(args, 4, 6)?;
                let (rate, per, nper, pv) = (a.num(0)?, a.num(1)?, a.num(2)?, a.num(3)?);
                let fv = a.opt_num(4)?.unwrap_or(0.0);
                let t = normalize_payment_type(a.opt_num(5)?);
                if per < 1.0 || per > nper || !per.is_finite() {
                    return Err(a.invalid());
                }
                let pmt = calculate_pmt(rate, nper, pv, fv, t);
                let balance = balance_before(rate, pv, pmt, t, per as i64);
                Ok(Value::Number(if t == 1.0 && per == 1.0 { 0.0 } else { -(balance * rate) }))
            }),
```

## !!steps Declining balance, with a straight line escape

`VDB` is the most involved of the five depreciation functions. It walks the
asset's life in slices of at most one period — the fractional `start` and
`end` bounds are what force the `min` on `next` — and at each slice computes
two candidates: the declining-balance amount at `factor / life`, and the
straight-line amount that would write the remaining book value down to
salvage over the remaining life.

Taking `ddb.max(sln)` is the switch: once straight-line depreciates faster,
it wins for the rest of the schedule, unless the optional `no_switch`
argument suppresses it. The result is then clamped so the book value never
falls below salvage, and only slices at or after `start` are accumulated —
which is how the same loop serves both the depreciation of a single period
and of a range.

```rust ! financial.rs
            eval: util::pure_fn(|args| {
                let a = Args::new(args, 5, 7)?;
                let (cost, salvage, life) = (a.num(0)?, a.num(1)?, a.num(2)?);
                let (start, end) = (a.num(3)?, a.num(4)?);
                let factor = a.opt_num(5)?.unwrap_or(2.0);
                let no_switch = a.values.get(6).map(|v| v.to_bool()).transpose()?.unwrap_or(false);
                if life <= 0.0 || start < 0.0 || end < start || end > life || factor <= 0.0 {
                    return Err(a.invalid());
                }
                if cost <= 0.0 {
                    return Ok(Value::Number(0.0));
                }
                let rate = factor / life;
                let mut value = cost;
                let mut total = 0.0;
                let mut period = 0.0;
                while period < end {
                    let next = (period + 1.0).min(end);
                    let frac = next - period;
                    let ddb = value * rate * frac;
                    let sln = if life - period > 0.0 {
                        (value - salvage) / (life - period) * frac
                    } else {
                        0.0
                    };
                    // !mark(1:2)
                    let dep = if no_switch { ddb } else { ddb.max(sln) };
                    let dep = dep.min(value - salvage).max(0.0);
                    if period >= start {
                        total += dep;
                    }
                    value -= dep;
                    period = next;
                }
                Ok(Value::Number(total))
            }),
```

## !!steps Newton Raphson, then a fallback

`RATE`, `IRR`, and `XIRR` have no closed form, so each runs the same shape of
solver: at most 100 Newton-Raphson steps from a guess that defaults to `0.1`,
accumulating the objective and its derivative in one pass, bailing out when
the derivative is smaller than `1e-15` or when successive rates differ by less
than `1e-10`.

`IRR` first insists on at least two cash flows with at least one of each sign,
since a series that never crosses zero has no rate of return. Note the
exponent: `IRR` discounts the first flow at period 0, whereas `NPV` discounts
its first value at period 1 — the two functions do not treat their inputs
alike. When Newton lands somewhere non-finite or at or below `-1.0`, the
closure hands its `npv_at` objective to `bisect`; `RATE` does the same, with
the slightly looser test `rate < -1.0`.

```rust ! financial.rs
            eval: util::pure_fn(|args| {
                let a = Args::new(args, 1, 2)?;
                let cash_flows = a.numbers_of(0);
                let guess = a.opt_num(1)?.unwrap_or(0.1);
                // ...
                let npv_at = |rate: f64| {
                    cash_flows
                        .iter()
                        .enumerate()
                        .map(|(i, &cf)| cf / (1.0 + rate).powi(i as i32))
                        .sum::<f64>()
                };

                let mut rate = guess;
                for _ in 0..100 {
                    let mut npv = 0.0;
                    let mut dnpv = 0.0;
                    for (i, &cf) in cash_flows.iter().enumerate() {
                        let factor = (1.0 + rate).powi(i as i32);
                        npv += cf / factor;
                        dnpv -= (i as f64) * cf / factor / (1.0 + rate);
                    }
                    if dnpv.abs() < 1e-15 {
                        break;
                    }
                    let new_rate = rate - npv / dnpv;
                    if (new_rate - rate).abs() < 1e-10 {
                        rate = new_rate;
                        break;
                    }
                    rate = new_rate;
                }

                // !mark(1:3)
                if !rate.is_finite() || rate <= -1.0 {
                    rate = bisect(npv_at).ok_or_else(|| a.invalid())?;
                }
                Ok(Value::Number(rate))
            }),
```

## !!steps The bisection fallback

`bisect` is what the module header calls out as an addition the modern core
lacks: a slower but far more robust second attempt. It sweeps 400 sample
points across the interval from just above `-1.0` (where the discount factors
blow up) to a rate of 10, looking for the first pair of finite samples whose
values have opposite signs. No sign change means no bracketed root, and the
`?` on `bracket` returns `None`, which the callers turn into an error.

With a bracket in hand it runs 200 halvings — far more than needed for `f64`
precision, but cheap and unconditional — keeping the half that still straddles
the sign change and returning the midpoint. A non-finite evaluation anywhere
in the refinement aborts rather than propagating a NaN into the answer.

```rust ! financial.rs
/// Bisection fallback for the rate solvers: scans (-0.9999, 10) for a sign
/// change of `f`, then halves the bracket. Returns None when no root is
/// bracketed.
fn bisect(f: impl Fn(f64) -> f64) -> Option<f64> {
    const STEPS: usize = 400;
    let x = |i: usize| -0.9999 + (10.0 + 0.9999) * i as f64 / STEPS as f64;
    let mut lo = x(0);
    let mut flo = f(lo);
    let mut bracket = None;
    for i in 1..=STEPS {
        let hi = x(i);
        let fhi = f(hi);
        // !mark
        if flo.is_finite() && fhi.is_finite() && flo * fhi <= 0.0 {
            bracket = Some((lo, hi));
            break;
        }
        lo = hi;
        flo = fhi;
    }
    let (mut lo, mut hi) = bracket?;
    let mut flo = f(lo);
    for _ in 0..200 {
        let mid = (lo + hi) / 2.0;
        let fm = f(mid);
        if !fm.is_finite() {
            return None;
        }
        if flo * fm <= 0.0 {
            hi = mid;
        } else {
            lo = mid;
            flo = fm;
        }
    }
    Some((lo + hi) / 2.0)
}
```

## !!steps Flat arguments, and cash flows on arbitrary dates

`pure_fn` hands each closure a single flat `Spanned<Vec<Spanned<Value>>>`, so
this file wraps it in a small `Args` struct: `Args::new` enforces the arity
window up front and reports `FormulaErrorMsg::BadArgumentCount` against the
call's span, `num` and `opt_num` read a required or optional scalar, and the
two accessors below flatten a whole argument — a range, an inline array, or a
scalar — into a list. `days_of` stringifies each element and pushes it through
`parse_date_str` and `days_from_civil` from
[datetime.rs](/docs/quadratic-core/src/formulas/functions/datetime.rs), so
dates arrive as plain day counts with the offending argument's span attached
to any parse error.

`XNPV` and `XIRR` build on that to drop the assumption that flows are evenly
spaced. Both require the value and date lists to have equal, non-empty
lengths, and both anchor on the *first* date in the list rather than on the
earliest one. Elapsed days become years by dividing by `365.0` — a flat
actual/365 count, the only day-count convention in this file; no function here
takes a basis argument. `XIRR` precomputes the same amount-and-years pairs
once and then runs the Newton loop from the previous steps over them.

```rust ! financial.rs
    fn numbers_of(&self, i: usize) -> Vec<f64> {
        util::flat_iter_numbers(&self.values[i..=i]).collect()
    }

    /// Dates of argument `i` as day counts, arrays flattened.
    fn days_of(&self, i: usize) -> FormulaResult<Vec<i64>> {
        let strings: Vec<String> = util::flat_iter_strings(&self.values[i..=i]).collect();
        strings
            .iter()
            .map(|s| {
                // !mark
                parse_date_str(s).map(|(y, m, d)| days_from_civil(y, m, d)).ok_or_else(|| {
                    FormulaErrorMsg::Expected {
                        expected: "a date like 2026-08-06".into(),
                        got: Some(s.clone().into()),
                    }
                    .with_span(self.values[i].span)
                })
            })
            .collect()
    }

// ...

            eval: util::pure_fn(|args| {
                let a = Args::new(args, 3, 3)?;
                let rate = a.num(0)?;
                let values = a.numbers_of(1);
                let days = a.days_of(2)?;
                if values.len() != days.len() || values.is_empty() {
                    return Err(a.invalid());
                }
                let d0 = days[0];
                let xnpv = values
                    .iter()
                    .zip(&days)
                    // !mark
                    .map(|(&v, &d)| v / (1.0 + rate).powf((d - d0) as f64 / 365.0))
                    .sum::<f64>();
                Ok(Value::Number(xnpv))
            }),
```
