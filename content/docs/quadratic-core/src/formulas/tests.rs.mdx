`formulas/mod.rs` declares this module as `#[cfg(test)] mod tests;`, so it
exists only when the crate is compiled by `cargo test`. It plays two roles at
once: it is the shared **test harness** — a pair of fake grids plus an `eval`
helper that every function module pulls in with `use crate::formulas::tests::*`
(logic, string, lookup, statistics, and eight others) — and it is the home of the
engine-level tests that no single built-in function owns: reference resolution,
circular references, array broadcasting, and parser regressions.

Reading it is the fastest way to learn what the engine actually promises. Each
test states a formula source string and the value it must produce.

<Scrollycoding>

## !!steps A grid that panics when read

`NoGrid` implements [GridProxy](/docs/quadratic-core/src/formulas/grid_proxy.rs)
by panicking. It is not a stub for convenience — it is an assertion: a test that
evaluates against `NoGrid` claims the formula never touches the spreadsheet at
all, and the panic message fires if that claim is wrong.

`eval` is the whole pipeline in three lines: parse the source at the origin, run
it at the origin, and drop the span from the result.
`eval_blocking` exists because [GridProxy::get](/docs/quadratic-core/src/formulas/grid_proxy.rs)
is `async` (the browser fetches cells from JS), so
[ast.rs](/docs/quadratic-core/src/formulas/ast.rs) wraps the future in
`pollster::block_on` for synchronous callers like these tests.

```rust ! tests.rs
use async_trait::async_trait;
use smallvec::smallvec;
use std::fmt;

pub(crate) use super::*;

/// `GridProxy` implementation that just panics whenever a cell is accessed.
#[derive(Debug, Default, Copy, Clone)]
pub(crate) struct NoGrid;
#[async_trait(?Send)]
impl GridProxy for NoGrid {
    async fn get(&mut self, _pos: Pos) -> Option<String> {
        // !mark
        panic!("no cell should be accessed")
    }
}

pub(crate) fn eval_to_string(grid: &mut dyn GridProxy, s: &str) -> String {
    eval(grid, s).unwrap().to_string()
}
pub(crate) fn eval(grid: &mut dyn GridProxy, s: &str) -> FormulaResult {
    parse_formula(s, Pos::ORIGIN)?
        .eval_blocking(grid, Pos::ORIGIN)
        .map(|value| value.inner)
}
```

## !!steps A grid backed by a closure

The other fake grid wraps any `FnMut(Pos) -> Option<String>`, which lets a test
define its spreadsheet inline — usually as a `match` on `(pos.x, pos.y)`, or as
an arithmetic formula over the coordinates. Returning `None` means "empty cell".

Two details are worth noting. The `where` bound is repeated on the tuple struct
itself, with a comment explaining why: it helps type inference when a test
writes `FnGrid(|pos| ...)` without naming the closure type. And `Debug` is
implemented by hand with `finish_non_exhaustive`, because a closure has no
`Debug` of its own yet the surrounding assertion machinery wants one.

```rust ! tests.rs
/// `GridProxy` implementation that calls a function for grid access.
#[derive(Copy, Clone)]
pub(crate) struct FnGrid<F>(pub F)
// Include `where` bounds here to help type inference when constructing.
where
    F: FnMut(Pos) -> Option<String>;
impl<F> fmt::Debug for FnGrid<F>
where
    F: FnMut(Pos) -> Option<String>,
{
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.debug_struct("FnGrid").finish_non_exhaustive()
    }
}
#[async_trait(?Send)]
impl<F> GridProxy for FnGrid<F>
where
    F: FnMut(Pos) -> Option<String>,
{
    async fn get(&mut self, pos: Pos) -> Option<String> {
        // !mark
        self.0(pos)
    }
}
```

## !!steps References resolve against the evaluating cell

This is the engine's most load-bearing behavior, and the test is deliberately
awkward: the formula is *parsed* at `D4` but *evaluated* at `B2`. A `$` freezes
a coordinate, so `$D$4` stays at `D4`; everything else stores an offset from the
parse position and is re-resolved from the evaluation position — the comments in
the closure spell out each landing spot, and the powers of ten make the sum
`11111` prove that all five arrived where expected.

The same formula evaluated at `D4` returns `FormulaErrorMsg::CircularReference`,
because `$D$4` then resolves onto the cell doing the evaluating. A companion
test, `test_formula_circular_array_ref`, checks the range case: `$B$0:$C$4`
evaluated at `B2` errors the same way, and its `FnGrid` panics if `B2` is ever
fetched — so the circularity is caught before any read happens.

```rust ! tests.rs
#[test]
fn test_formula_cell_ref() {
    let form = parse_formula("SUM($D$4, $B0, E$n6, B0, nB2)", pos![D4]).unwrap();

    let mut g = FnGrid(|pos| {
        Some(match (pos.x, pos.y) {
            // The formula was parsed at D4, but we'll be evaluating it from B2 so
            // adjust the cell coordinates accordingly.
            (3, 4) => "1".to_string(),      // $D$4 -> D4
            (1, -2) => "10".to_string(),    // $B0  -> Bn2
            (2, -6) => "100".to_string(),   // E$n6 -> Cn6
            (-1, -2) => "1000".to_string(), // B0   -> nAn2
            (-4, 0) => "10000".to_string(), // nB2  -> nD0
            _ => panic!("cell {pos} shouldn't be accessed"),
        })
    });

    // Evaluate at D4, causing a circular reference.
    // !mark(1:4)
    assert_eq!(
        FormulaErrorMsg::CircularReference,
        form.eval_blocking(&mut g, pos![D4]).unwrap_err().msg,
    );

    // Evaluate at B2
    assert_eq!(
        "11111".to_string(),
        form.eval_blocking(&mut g, pos![B2]).unwrap().to_string(),
    );
}
```

## !!steps Arrays broadcast across operators

Here the fake grid is a formula itself — cell `(x, y)` contains `x * 10 + y` —
so every expected product can be written out longhand and checked against the
address it came from. The four assertions cover the whole broadcasting matrix:
scalar times scalar, array times scalar, scalar times array, and array times
array elementwise.

The final assertion pins the failure mode: two arrays of different shapes do not
silently pad or truncate, they produce the message
`Array size mismatch: expected (4, 2), got (5, 2)`.

```rust ! tests.rs
#[test]
fn test_formula_array_op() {
    let mut g = FnGrid(|pos| Some((pos.x * 10 + pos.y).to_string()));

    let f = |x| Value::Number(x as f64);

    assert_eq!((11 * 31).to_string(), eval_to_string(&mut g, "B1 * D1"));
    assert_eq!(
        Value::Array(vec![
            smallvec![f(11 * 31), f(21 * 31)],
            smallvec![f(12 * 31), f(22 * 31)],
            smallvec![f(13 * 31), f(23 * 31)],
            smallvec![f(14 * 31), f(24 * 31)],
        ]),
        eval(&mut g, "B1:C4 * D1").unwrap(),
    );
    // ...
    // !mark(1:4)
    assert_eq!(
        "Array size mismatch: expected (4, 2), got (5, 2)",
        eval(&mut g, "B1:C4 * D1:E5").unwrap_err().msg.to_string(),
    );
}
```

## !!steps Array literal syntax

Arrays can also be written directly: commas separate columns, semicolons
separate rows. The second assertion is a round trip through `Display` — messy
input spacing normalizes to `{11, 12; 21, 22; 31, 32}`, which is the form the
app shows in a cell.

The rest of the test fences off what is *not* allowed: rows of unequal length
give `NonRectangularArray`, and an empty array or an empty row is an error
rather than an empty value. Related, `test_formula_range_operator` checks the
`..` operator: every spacing variant of `1 .. 5` (and forms like `.9` and `5.`)
evaluates to the column array `{1; 2; 3; 4; 5}`, while `1...5` is rejected with
`Unexpected("ellipsis")`.

```rust ! tests.rs
#[test]
fn test_array_parsing() {
    let f = |x| Value::Number(x as f64);
    assert_eq!(
        Value::Array(vec![
            smallvec![f(11), f(12)],
            smallvec![f(21), f(22)],
            smallvec![f(31), f(32)],
        ]),
        eval(&mut NoGrid, "{11, 12; 21, 22; 31, 32}").unwrap(),
    );

    // Test stringification
    assert_eq!(
        "{11, 12; 21, 22; 31, 32}",
        eval_to_string(&mut NoGrid, "{11,   12 ;21, 22;31,32}"),
    );
    // ...
    // Mismatched rows
    // !mark(1:4)
    assert_eq!(
        FormulaErrorMsg::NonRectangularArray,
        eval(&mut NoGrid, "{1; 3, 4}").unwrap_err().msg,
    );

    // Empty array
    assert!(eval(&mut NoGrid, "{}").is_err());
    assert!(eval(&mut NoGrid, "{ }").is_err());

    // Empty row
    assert!(eval(&mut NoGrid, "{ ; }").is_err());
}
```

## !!steps Regressions from the issue tracker

Three small tests, each guarding a spreadsheet habit that a naive parser gets
wrong. A user typing `=3+4` expects the leading `=` to be a marker, not an
operator — that is handled in `Parser::new`, which consumes a leading `=` and
rewinds if it is not there.

`Z1-5` must lex as a reference minus five, not as the reference `Z1-5`; the
spaced and unspaced forms both have to give `25`. And `"$10" + 20` must coerce
the currency-formatted string to `10`, giving `30`, rather than choking on the
dollar sign that also introduces absolute references.

```rust ! tests.rs
#[test]
fn test_leading_equals() {
    assert_eq!("7", eval_to_string(&mut NoGrid, "=3+4"));
    assert_eq!("7", eval_to_string(&mut NoGrid, "= 3+4"));
}

/// Regression test for quadratic#253
#[test]
fn test_hyphen_after_cell_ref() {
    let mut g = FnGrid(|_| Some("30".to_string()));
    assert_eq!("25", eval_to_string(&mut g, "Z1 - 5"));
    // !mark
    assert_eq!("25", eval_to_string(&mut g, "Z1-5"));
}
// ...
/// Regression test for quadratic#410
#[test]
fn test_currency_string() {
    assert_eq!("30", eval_to_string(&mut NoGrid, "\"$10\" + 20"));
}
```

## !!steps Finding cell references without evaluating

`find_cell_references` is the engine's second public entry point. The wasm layer
in [lib.rs](/docs/quadratic-core/src/lib.rs) returns its output to JavaScript
next to any parse error, and `relocate_formula` uses it to rewrite a formula's
references when a cell is copied — so it has to survive half-written input.
The source string here is deliberately broken:
`:D$n6` and `A0:` are dangling range halves, and the scan still recovers the
complete references around them.

The assertions read the results as `CellRefCoord` values, which is where the
`$` distinction becomes visible: `Absolute(col![A])` stores the column
literally, while `Relative(7 - base.y)` stores an offset from the base position
`D4`. The test ends by asserting the iterator is exhausted, so nothing extra was
matched.

```rust ! tests.rs
#[test]
fn test_find_cell_references() {
    use CellRefCoord::{Absolute, Relative};

    // Evaluate at D4.
    let base = pos![D4];
    // !mark
    let refs = find_cell_references("SUM($C$4, $A0 : nQ7, :D$n6, A0:, ZB2)", base);
    let mut iter = refs.iter().map(|r| r.inner);

    // $C$4
    assert_eq!(
        iter.next(),
        Some(RangeRef::Cell(CellRef::absolute(pos![C4]))),
    );

    // $A0:nQ7
    assert_eq!(
        iter.next(),
        Some(RangeRef::CellRange(
            CellRef {
                x: Absolute(col![A]),
                y: Relative(0 - base.y),
            },
            CellRef {
                x: Relative(col![nQ] - base.x),
                y: Relative(7 - base.y),
            },
        )),
    );
    // ...
    assert_eq!(iter.next(), None);
}
```
