The first stage of the formula engine. `lexer.rs` turns raw formula text into a
stream of `Spanned<Token>` — a token kind plus the byte range it came from. Its
module doc calls this *lossless* tokenization: nothing is thrown away, not
whitespace and not comments, so the byte offsets always line up with the
original source string.

Losslessness matters twice over. The [parser](/docs/quadratic-core/src/formulas/parser/mod.rs)
skips whitespace and comments itself while keeping accurate spans for error
messages, and `find_cell_references` re-lexes the same source to hand the app a
list of cell references with byte ranges that still index into the user's
original text.

## !!steps One token at a time

`tokenize` is the whole public surface: it returns a lazy iterator built from
`std::iter::from_fn`. The closure owns a single piece of mutable state,
`token_start`, and each call asks `Token::consume_from_input` for the next
token plus the index just past it. That pair becomes a `Span`, `token_start`
advances to the end, and the token is wrapped as a `Spanned` value.

Because the end of one token is the start of the next, the spans tile the input
with no gaps — the losslessness guarantee falls straight out of this loop.

```rust ! lexer.rs
pub fn tokenize(input_str: &str) -> impl '_ + Iterator<Item = Spanned<Token>> {
    let mut token_start = 0;
    std::iter::from_fn(move || {
        Token::consume_from_input(input_str, token_start).map(|(token, token_end)| {
            let span = Span {
                start: token_start,
                end: token_end,
            };
            // !mark
            token_start = token_end;
            Spanned { span, inner: token }
        })
    })
}
```

## !!steps The interesting patterns, documented in ASCII

Three of the token patterns are complicated enough to earn their own constants,
each with an ASCII diagram in the doc comment explaining the regex column by
column. A function call is an identifier *terminated by* an open paren, so
`SUM(` lexes as one token rather than a name followed by a paren.

A cell reference allows optional `$` for absolute addressing and optional `n`
for negative coordinates, on both the column and the row. Numeric literals
carry no leading sign — a minus sign is always lexed as its own operator token
and resolved later by the parser.

```rust ! lexer.rs
/// Function call consisting of a letter or underscore followed by any letters,
/// digits, and/or underscores terminated with a `(`.
const FUNCTION_CALL_PATTERN: &str = r#"[A-Za-z_][A-Za-z_\d]*\("#;

/// A1-style cell reference.
///
/// \$?n?[A-Z]+\$?n?\d+
/// \$?        \$?            optional `$`s
///    n?         n?          optional `n`s
///      [A-Z]+               letters
///                 \d+       digits
// !mark
const A1_CELL_REFERENCE_PATTERN: &str = r#"\$?n?[A-Z]+\$?n?\d+"#;

/// Floating-point or integer number, without leading sign.
///
/// (\d+(\.\d*)?|\.\d+)([eE][+-]?\d+)?
/// (           |     )                   EITHER
///  \d+                                    integer part
///     (\.\d*)?                            with an optional decimal
/// (           |     )                   OR
///              \.\d+                      decimal part only
///                    ([eE]        )?    optional exponent
///                         [+-]?           with an optional sign
///                              \d+        followed by some digits
const NUMERIC_LITERAL_PATTERN: &str = r#"(\d+(\.\d*)?|\.\d+)([eE][+-]?\d+)?"#;
```

## !!steps Order is the disambiguation rule

All the patterns live in one ordered list, and the comment states the invariant:
"arranged roughly from least to most general". Regex alternation in the `regex`
crate prefers the leftmost alternative that matches at the earliest position, so
putting two-character comparisons like `<=` before the catch-all is what stops
them from being split into two single-character tokens.

The last entry, `[\s\S]`, matches any single character including newlines. It
guarantees the lexer always makes progress: whatever the input, something
matches, and the worst case is a one-character `Unknown` token.

```rust ! lexer.rs
const TOKEN_PATTERNS: &[&str] = &[
    // Comparison operators `==`, `!=`, `<=`, and `>=`.
    r#"[=!<>]="#,
    // Double and triple dot.
    r#"\.\.\.?"#,
    // Line comment.
    r#"//[^\n]*"#,
    // Start of a block comment (block comment has special handling).
    r#"/\*"#,
    // String literal.
    SINGLE_QUOTE_STRING_LITERAL_PATTERN,
    DOUBLE_QUOTE_STRING_LITERAL_PATTERN,
    UNTERMINATED_STRING_LITERAL_PATTERN,
    // Numeric literal.
    NUMERIC_LITERAL_PATTERN,
    // Function call.
    FUNCTION_CALL_PATTERN,
    // Reference to a cell.
    A1_CELL_REFERENCE_PATTERN,
    // Whitespace.
    r#"\s+"#,
    // Any other single Unicode character.
    // !mark
    r#"[\s\S]"#,
];
```

## !!steps Two flavors of compiled regex

Each pattern gets used two different ways, so it is compiled twice. `TOKEN_REGEX`
joins the whole list with `|` and is used to *find* the next token anywhere in
the input. The per-pattern regexes go through `new_fullmatch_regex`, which wraps
the pattern as `^(...)` so it can be used to *classify* a string the tokenizer
has already sliced off.

Both sets are `lazy_static`, so the regexes compile once on first use rather
than on every formula evaluation.

```rust ! lexer.rs
fn new_fullmatch_regex(s: &str) -> Regex {
    Regex::new(&("^(".to_owned() + s + ")")).unwrap()
}

// ...

lazy_static! {
    /// Single regex that matches any token, including comments and strings,
    /// by joining each member of `TOKEN_PATTERNS` with "|".
    // !mark
    pub static ref TOKEN_REGEX: Regex =
        Regex::new(&TOKEN_PATTERNS.join("|")).unwrap();

    /// Regex that matches a valid function call.
    pub static ref FUNCTION_CALL_REGEX: Regex =
        new_fullmatch_regex(FUNCTION_CALL_PATTERN);

    /// Regex that matches a valid A1-style cell reference.
    pub static ref A1_CELL_REFERENCE_REGEX: Regex =
        new_fullmatch_regex(A1_CELL_REFERENCE_PATTERN);

    /// Regex that matches all valid numeric literals and some invalid ones.
    pub static ref NUMERIC_LITERAL_REGEX: Regex =
        new_fullmatch_regex(NUMERIC_LITERAL_PATTERN);

    /// Regex that matches a valid string literal.
    pub static ref STRING_LITERAL_REGEX: Regex =
        new_fullmatch_regex(&[
            SINGLE_QUOTE_STRING_LITERAL_PATTERN,
            DOUBLE_QUOTE_STRING_LITERAL_PATTERN,
        ].join("|"));

    /// Regex that matches an unterminated string literal.
    pub static ref UNTERMINATED_STRING_LITERAL_REGEX: Regex =
        new_fullmatch_regex(UNTERMINATED_STRING_LITERAL_PATTERN);
}
```

## !!steps Tokens that know how to describe themselves

`Token` is a plain `Copy` enum with no payload — the text of a token is
recovered from its span, not stored on the variant. Every variant carries a
`strum` `to_string` attribute giving a human phrase like "argument separator
(comma)", which is what the parser prints in "expected …" errors.

Note the deliberately non-fatal variants: `UnterminatedBlockComment`,
`UnterminatedStringLiteral`, and `Unknown`. The lexer never fails; malformed
input still produces tokens, and it is the parser's job to reject them with a
span pointing at the offending text.

```rust ! lexer.rs
#[derive(Debug, Display, Copy, Clone, PartialEq, Eq)]
pub enum Token {
    // Grouping
    #[strum(to_string = "left paren")]
    LParen,
    #[strum(to_string = "left bracket")]
    LBracket,
    #[strum(to_string = "left brace")]
    LBrace,
    #[strum(to_string = "right paren")]
    RParen,
    #[strum(to_string = "right bracket")]
    RBracket,
    #[strum(to_string = "right brace")]
    RBrace,

    // ...

    // Other special tokens
    #[strum(to_string = "function call")]
    FunctionCall,
    #[strum(to_string = "string literal")]
    StringLiteral,
    #[strum(to_string = "unterminated string literal")]
    UnterminatedStringLiteral,
    #[strum(to_string = "numeric literal")]
    NumericLiteral,
    #[strum(to_string = "cell reference")]
    CellRef,
    #[strum(to_string = "whitespace")]
    Whitespace,
    #[strum(to_string = "unknown symbol")]
    Unknown,
}
```

## !!steps Classifying the matched text

`consume_from_input` starts with `TOKEN_REGEX.find_at`, which searches from
`start` and returns `None` at end of input — that `?` is what terminates the
iterator. The match text is then classified by an ordinary `match`, beginning
with the fixed symbols.

Two aliasing decisions show up here: both `=` and `==` produce `Eql`, and both
`<>` (the spreadsheet spelling) and `!=` produce `Neq`. Note also that `end` is
declared `mut` — the block comment arm below rewrites it.

```rust ! lexer.rs
impl Token {
    /// Consumes a token from a given starting index and returns the index of
    /// the next character after the token.
    fn consume_from_input(input_str: &str, start: usize) -> Option<(Self, usize)> {
        // Find next token.
        let m = TOKEN_REGEX.find_at(input_str, start)?;

        // !mark
        let mut end = m.end();

        let token = match m.as_str() {
            "(" => Self::LParen,
            "[" => Self::LBracket,
            "{" => Self::LBrace,
            ")" => Self::RParen,
            "]" => Self::RBracket,
            "}" => Self::RBrace,
            "," => Self::ArgSep,
            ";" => Self::RowSep,
            // !mark(1:2)
            "=" | "==" => Self::Eql,
            "<>" | "!=" => Self::Neq,
            "<" => Self::Lt,
            ">" => Self::Gt,
            "<=" => Self::Lte,
            ">=" => Self::Gte,
            "+" => Self::Plus,
            "-" => Self::Minus,
            "*" => Self::Mult,
            "/" => Self::Div,
            "^" => Self::Power,
            "&" => Self::Concat,
            ".." => Self::RangeOp,
            "%" => Self::Percent,
            ":" => Self::CellRangeOp,
            "..." => Self::Ellipsis,

            // ...
```

## !!steps Block comments nest, so regex alone cannot do it

`TOKEN_PATTERNS` only matches the opening `/*`; the rest is hand-scanned here,
because nesting is not a regular language. A second regex finds every `/*` and
`*/` boundary in the remaining input and a depth counter walks them, incrementing
on open and decrementing on close, stopping as soon as depth returns to zero.

If depth comes back to zero the token is a normal `Comment` and `end` is
rewritten to the real closing position; otherwise the input ran out and the
token is `UnterminatedBlockComment`, which keeps the span running to the end of
the file. The tests at the bottom of the file pin this behavior down, including
the delightful `/* nested /*/ oh my! ***/*/`.

```rust ! lexer.rs
            // Match a line comment.
            s if s.starts_with("//") => Self::Comment,

            // Match a block comment.
            s if s.starts_with("/*") => {
                lazy_static! {
                    static ref COMMENT_BOUNDARY_PATTERN: Regex = Regex::new(r"/\*|\*/").unwrap();
                }
                let mut depth = 0;
                let mut comment_len = 0;
                for m in COMMENT_BOUNDARY_PATTERN.find_iter(&input_str[start..]) {
                    comment_len = m.end();
                    match m.as_str() {
                        // !mark(1:2)
                        "/*" => depth += 1,
                        "*/" => depth -= 1,
                        _ => (), // should be impossible
                    }
                    if depth <= 0 {
                        break;
                    }
                }
                if depth == 0 {
                    end = start + comment_len;
                    Self::Comment
                } else {
                    Self::UnterminatedBlockComment
                }
            }
```

## !!steps Fallbacks, a range fixup, and what the parser ignores

Everything else is classified by re-matching the slice against the anchored
regexes, again ordered specific-to-general and ending with `Unknown`. Then comes
a genuine ambiguity fix: `1..5` would otherwise lex as the numeric literal `1.`
followed by `.5`, so when a numeric literal ends in `.` and the next character
is also `.`, the token gives the dot back by decrementing `end`. The comment is
honest that this still fails on `1...5`, which is ambiguous between `1 .. .5`
and `1. .. 5`.

Finally, `is_skip` marks comments and whitespace as the tokens the parser steps
over by default — the reason the lexer can keep them without complicating every
syntax rule.

```rust ! lexer.rs
            // Match anything else.
            s if FUNCTION_CALL_REGEX.is_match(s) => Self::FunctionCall,
            s if STRING_LITERAL_REGEX.is_match(s) => Self::StringLiteral,
            s if UNTERMINATED_STRING_LITERAL_REGEX.is_match(s) => Self::UnterminatedStringLiteral,
            s if NUMERIC_LITERAL_REGEX.is_match(s) => Self::NumericLiteral,
            s if A1_CELL_REFERENCE_REGEX.is_match(s) => Self::CellRef,
            s if s.trim().is_empty() => Self::Whitespace,

            // Give up.
            _ => Self::Unknown,
        };

        let rest_of_input = &input_str[end..];

        // Special workaround for `<integer>..<number>`. This fails on `1...5`,
        // which is ambiguous between `1 .. .5` and `1. .. 5`.
        if token == Self::NumericLiteral
            && m.as_str().ends_with('.')
            && rest_of_input.starts_with('.')
        {
            // !mark
            end -= 1;
        }

        Some((token, end))
    }

    /// Returns whether this token is a comment or whitespace that should be
    /// skipped most of the time when parsing.
    pub fn is_skip(self) -> bool {
        matches!(self, Self::Comment | Self::Whitespace)
    }
}
```
