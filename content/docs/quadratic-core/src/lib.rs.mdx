`lib.rs` is the crate root of **quadratic-core**, the Rust formula engine that
ships to the browser as WebAssembly. Everything the SvelteKit app can call
lives here: each exported function is annotated with `#[wasm_bindgen]`, takes
plain numbers and strings, and hands back a `JsValue` serialized by
`serde_wasm_bindgen`.

The file has two halves. One is the exported API — evaluate a formula, parse
one, list the built-in functions, rewrite A1 references after an edit. The
other is `JsGridProxy`: the adapter that lets Rust ask JavaScript for a cell
value while evaluation is in flight, which is what makes the whole thing
async.

## !!steps Crate root and the wasm greeting

The module tree is small: `util` is declared with `#[macro_use]` so its
`jsexpr!`, `col!` and `pos!` macros are visible crate-wide, `formulas` holds
the lexer, parser, AST and function library, while `cell` and `position` are
private modules whose types are re-exported. `QUADRANT_SIZE` fixes the grid's
16-by-16 quadrant blocks that [position.rs](/docs/quadratic-core/src/position.rs)
uses.

The `extern "C"` block is the one import going the other way: it binds
JavaScript's `console.log` into Rust under the name `log`. `hello()` is
exported back out and called once by the app right after the wasm module
initializes, so a successful load is visible in the browser console.

```rust ! lib.rs
#![warn(rust_2018_idioms, clippy::semicolon_if_nothing_returned)]
#![allow(clippy::diverging_sub_expression, clippy::match_like_matches_macro)]

use async_trait::async_trait;
use itertools::Itertools;
use serde::{Deserialize, Serialize};
use std::collections::HashSet;
use wasm_bindgen::prelude::*;

#[macro_use]
pub mod util;
mod cell;
pub mod formulas;
mod position;

pub use cell::{Cell, CellTypes, JsCell};
use formulas::{GridProxy, Value};
pub use position::Pos;

// !mark
pub const QUADRANT_SIZE: u64 = 16;

#[wasm_bindgen]
extern "C" {
    // Use `js_namespace` here to bind `console.log(..)` instead of just
    // `log(..)`
    #[wasm_bindgen(js_namespace = console)]
    fn log(s: &str);
}

#[wasm_bindgen]
pub fn hello() {
    // say hello, when loaded successfully
    // !mark
    log("[WASM/Rust] quadratic-core ready");
}
```

## !!steps Evaluating a formula

`eval_formula` is the engine's main entry point. Its coordinates arrive as
`f64` because that is what JavaScript numbers are; they are cast to `i64` and
packed into a `Pos`. The fourth argument is a live JavaScript function —
`js_sys::Function` — which the app supplies as an async rectangle accessor.

Parsing and evaluation are one expression: parse against `pos` (relative
references need the formula cell as their base), then `await` the evaluation
with the proxy passed in mutably. Because the proxy records every cell it was
asked for, the accessed positions can be drained straight out of it afterwards
and flattened into `[x, y]` pairs — that list is how the app knows which cells
this formula depends on.

```rust ! lib.rs
/// Evaluates a formula and returns a formula result.
#[wasm_bindgen]
pub async fn eval_formula(
    formula_string: &str,
    x: f64,
    y: f64,
    grid_accessor_fn: js_sys::Function,
) -> JsValue {
    let mut grid_proxy = JsGridProxy::new(grid_accessor_fn);
    let x = x as i64;
    let y = y as i64;
    let pos = Pos { x, y };

    // !mark(1:4)
    let formula_result = match formulas::parse_formula(formula_string, pos) {
        Ok(formula) => formula.eval(&mut grid_proxy, pos).await,
        Err(e) => Err(e),
    };
    let cells_accessed = grid_proxy
        .cells_accessed
        .into_iter()
        .map(|pos| [pos.x, pos.y])
        .collect_vec();

    // ...
```

## !!steps Shaping the result for JavaScript

`JsFormulaResult` is a flat, JSON-friendly record: success flag, the accessed
cells, an optional error, and *two* optional output slots. It is private to
the crate but its serialized shape is mirrored on the TypeScript side by
`RunFormulaResult` in [runFormula.ts](/docs/src/lib/formulas/runFormula.ts).

The two output slots exist because a formula can produce either a scalar or a
spilled range. `Value::Array` is stringified row by row into
`Vec<Vec<String>>` and lands in `array_output`; anything else is stringified
once into `output_value`. Exactly one of the two is `Some` on success, so the
caller can tell a spill from a single value without inspecting types.

```rust ! lib.rs
#[derive(Serialize, Deserialize, Debug, Clone)]
struct JsFormulaResult {
    pub cells_accessed: Vec<[i64; 2]>,
    pub success: bool,
    pub error_span: Option<[usize; 2]>,
    pub error_msg: Option<String>,
    pub output_value: Option<String>,
    pub array_output: Option<Vec<Vec<String>>>,
}

// ...

    let result = match formula_result {
        Ok(formula_output) => {
            let mut output_value = None;
            let mut array_output = None;
            match formula_output.inner {
                // !mark
                Value::Array(a) => {
                    array_output = Some(
                        a.iter()
                            .map(|row| row.iter().map(|cell| cell.to_string()).collect())
                            .collect(),
                    );
                }
                non_array_value => output_value = Some(non_array_value.to_string()),
            };
            JsFormulaResult {
                cells_accessed,
                success: true,
                error_span: None,
                error_msg: None,
                output_value,
                array_output,
            }
        }
```

## !!steps When evaluation fails

Errors never cross the wasm boundary as exceptions. A failed parse or a failed
evaluation becomes the same record with `success: false`, the error message as
a string, and the error's byte span reduced to a `[start, end]` pair so the
editor can underline the offending text.

`cells_accessed` is filled in on the error path too: a formula that read three
cells and then divided by zero still depends on those three cells. The whole
struct is converted in one call to `serde_wasm_bindgen::to_value`, which is
what makes the return type a bare `JsValue`.

```rust ! lib.rs
        Err(error) => JsFormulaResult {
            cells_accessed,
            success: false,
            // !mark
            error_span: error.span.map(|span| [span.start, span.end]),
            error_msg: Some(error.msg.to_string()),
            output_value: None,
            array_output: None,
        },
    };

    serde_wasm_bindgen::to_value(&result).unwrap()
}
```

## !!steps The JsGridProxy bridge

This is the seam between the two languages. `JsGridProxy` holds the JavaScript
callback the app handed to `eval_formula`, plus a `HashSet` of every `Pos` it
has been asked about. Recording happens in `get_cell_jsvalue` *before* the
call, so a cell counts as a dependency even when it turns out to be empty.

The call itself is written with the crate's `jsexpr!` macro from
[util.rs](/docs/quadratic-core/src/util.rs), which mimics JavaScript syntax:
invoke the function with four coordinates, `await` the returned promise, take
element `0`, read its `value` property. The engine only ever needs one cell,
so it asks for the degenerate rectangle from `(x, y)` to `(x, y)`.
Implementing [GridProxy](/docs/quadratic-core/src/formulas/grid_proxy.rs)
requires `#[async_trait(?Send)]` because `JsValue` cannot move between
threads; `get` simply drops both failure modes — a rejected promise and a
non-string value — into `None`, which the evaluator reads as an empty cell.

```rust ! lib.rs
#[derive(Debug, Clone)]
struct JsGridProxy {
    grid_accessor_fn: js_sys::Function,
    cells_accessed: HashSet<Pos>,
}
impl JsGridProxy {
    fn new(grid_accessor_fn: js_sys::Function) -> Self {
        Self {
            grid_accessor_fn,
            cells_accessed: HashSet::new(),
        }
    }

    async fn get_cell_jsvalue(&mut self, pos: Pos) -> Result<JsValue, JsValue> {
        // Record that we accessed this cell.
        // !mark
        self.cells_accessed.insert(pos);

        let grid_accessor_fn = self.grid_accessor_fn.clone();
        let x: JsValue = pos.x.into();
        let y: JsValue = pos.y.into();
        // Access a rectangle of one cell, ranging from (x, y) to (x, y).
        // !mark
        Ok(jsexpr!(grid_accessor_fn(x, y, x, y).await[0].value))
    }
}
#[async_trait(?Send)]
impl GridProxy for JsGridProxy {
    async fn get(&mut self, pos: Pos) -> Option<String> {
        self.get_cell_jsvalue(pos).await.ok()?.as_string()
    }
}
```

## !!steps Parsing without evaluating

`parse_formula` runs the front end only — no grid access, so it needs no
callback and returns instantly. It reports two independent things: whether
parsing failed (message plus span) and where every cell reference sits in the
source text.

`find_cell_references` returns `Spanned<RangeRef>` values, which the `From`
impl above flattens into `JsCellRefSpan`. The doc comment on the function
carries a full JSON example of the output; it is generated by the
`example_parse_formula_output` test at the bottom of the file rather than
written by hand. Note the two error fields are independent: a message can be
present with no span.

```rust ! lib.rs
#[derive(Serialize, Deserialize, Debug, Default, Clone)]
pub struct JsFormulaParseResult {
    pub parse_error_msg: Option<String>,
    pub parse_error_span: Option<formulas::Span>,

    pub cell_refs: Vec<JsCellRefSpan>,
}
#[derive(Serialize, Deserialize, Debug, Copy, Clone)]
pub struct JsCellRefSpan {
    pub span: formulas::Span,
    pub cell_ref: formulas::RangeRef,
}

// ...

#[wasm_bindgen]
pub async fn parse_formula(formula_string: &str, x: f64, y: f64) -> JsValue {
    let x = x as i64;
    let y = y as i64;
    let pos = Pos { x, y };

    let parse_error = formulas::parse_formula(formula_string, pos).err();

    let result = JsFormulaParseResult {
        parse_error_msg: parse_error.as_ref().map(|e| e.msg.to_string()),
        parse_error_span: parse_error.and_then(|e| e.span),

        // !mark(1:4)
        cell_refs: formulas::find_cell_references(formula_string, pos)
            .into_iter()
            .map(|r| r.into())
            .collect(),
    };

    serde_wasm_bindgen::to_value(&result).unwrap()
}
```

## !!steps Function documentation for the app

`formula_docs` walks `formulas::functions::CATEGORIES`, skips any category
whose `include_in_docs` flag is false, sorts each category's functions by
name, and flattens everything into one `Vec<JsFunctionDoc>`. The category name
is repeated on every entry, so the JavaScript side can group without a nested
structure.

Each entry carries the signature strings, the examples, and the markdown doc
string that the function library declares. The app caches the result once and
renders it in
[FormulaDocs.svelte](/docs/src/lib/components/FormulaDocs.svelte); the same
data also feeds the offline reference produced by
[docgen.rs](/docs/quadratic-core/src/bin/docgen.rs).

```rust ! lib.rs
#[derive(Serialize, Deserialize, Debug, Clone)]
pub struct JsFunctionDoc {
    pub category: String,
    pub name: String,
    pub usages: Vec<String>,
    pub examples: Vec<String>,
    pub doc: String,
}

/// Returns documentation for every formula function, grouped by category,
/// for the in-app formula reference.
#[wasm_bindgen]
pub fn formula_docs() -> JsValue {
    let mut out: Vec<JsFunctionDoc> = vec![];
    for category in formulas::functions::CATEGORIES {
        // !mark
        if !category.include_in_docs {
            continue;
        }
        let mut functions = (category.get_functions)();
        functions.sort_by_key(|f| f.name);
        for f in functions {
            out.push(JsFunctionDoc {
                category: category.name.to_string(),
                name: f.name.to_string(),
                usages: f.usages_strings().collect(),
                examples: f.examples.iter().map(|s| s.to_string()).collect(),
                doc: f.doc.to_string(),
            });
        }
    }
    serde_wasm_bindgen::to_value(&out).unwrap()
}
```

## !!steps Adjusting references after an insert or delete

When a row or column is inserted or deleted, every formula on the sheet has to
be rewritten. `adjust_formula` takes the formula cell's position *before* the
edit, a flag for which axis moved, the coordinate `at` where the change
happened, and the signed `delta`. The `shift` closure is the whole rule:
coordinates at or past `at` move by `delta`, everything before it stays.

The formula cell itself moves too, which is why `new_base` is computed
alongside. That matters for relative references, which are stored as offsets
from the base: `adjust_coord` resolves the reference to an absolute target,
shifts that target, and then re-expresses it in the same flavour it had —
relative offsets are re-derived against `new_base`, absolute coordinates keep
their shifted value. `adjust_cell` (just below) applies this to whichever axis
moved and leaves the other one untouched.

```rust ! lib.rs
#[wasm_bindgen]
pub fn adjust_formula(
    formula_string: &str,
    cell_x: f64,
    cell_y: f64,
    is_column: bool,
    at: f64,
    delta: f64,
) -> String {
    use formulas::{CellRef, CellRefCoord, RangeRef};

    let old_base = Pos {
        x: cell_x as i64,
        y: cell_y as i64,
    };
    let at = at as i64;
    let delta = delta as i64;
    // !mark
    let shift = |v: i64| if v >= at { v + delta } else { v };
    let new_base = Pos {
        x: if is_column { shift(old_base.x) } else { old_base.x },
        y: if is_column { old_base.y } else { shift(old_base.y) },
    };

    // shifted-axis coordinate: recompute the target, keep the ref kind
    let adjust_coord = |c: CellRefCoord, old_axis_base: i64, new_axis_base: i64| {
        let target = shift(c.resolve_from(old_axis_base));
        match c {
            CellRefCoord::Relative(_) => CellRefCoord::Relative(target - new_axis_base),
            CellRefCoord::Absolute(_) => CellRefCoord::Absolute(target),
        }
    };
```

## !!steps Relocating a formula on copy

`relocate_formula` handles fill and paste, and it is strikingly short because
the reference representation already does the work. Relative coordinates are
stored as offsets from the base cell, absolute ones as fixed values, so simply
re-rendering an untouched `RangeRef` against `new_base` moves the relative
parts by the copy distance while `$` references print unchanged.

Both rewriting functions share the same splicing discipline: find the
references, sort them by span start, then walk the list **in reverse** and
`replace_range` each span. Editing right to left keeps every earlier span
valid even when the replacement text changes length, and any text that is not
a cell reference — string literals, function names, operators — is never
touched. `adjust_formula` ends with the same loop, plus a `match` that maps
each `RangeRef` variant through `adjust_cell`.

```rust ! lib.rs
/// Rewrites a formula's A1 references for a copy from one cell to another
/// (fill/paste semantics): relative references follow the copy offset,
/// `$` absolute references stay put.
#[wasm_bindgen]
pub fn relocate_formula(
    formula_string: &str,
    old_x: f64,
    old_y: f64,
    new_x: f64,
    new_y: f64,
) -> String {
    let old_base = Pos {
        x: old_x as i64,
        y: old_y as i64,
    };
    let new_base = Pos {
        x: new_x as i64,
        y: new_y as i64,
    };

    let mut refs = formulas::find_cell_references(formula_string, old_base);
    refs.sort_by_key(|r| r.span.start);

    let mut result = formula_string.to_string();
    // relative coords are stored as offsets, so re-rendering the same
    // RangeRef against the new base moves them; absolute coords ignore base
    // !mark(1:6)
    for r in refs.iter().rev() {
        result.replace_range(
            r.span.start as usize..r.span.end as usize,
            &r.inner.a1_string(new_base),
        );
    }
    result
}
```

## !!steps Column names and the unit tests

Two thin wrappers finish the exported surface. They forward to the real
implementations in [util.rs](/docs/quadratic-core/src/util.rs) and only adapt
types at the boundary: `f64` in, floored to `i64`; `Option<i64>` out, widened
to `Option<f64>` so wasm-bindgen can render it as `null`.

The test module exercises the two rewriting functions directly against string
literals, which doubles as the clearest specification of their behaviour: a
fill down by one row moves `SUM(B2:C2)` to `SUM(B3:C3)` while `$B$0` stays
put. The `test_adjust_formula` cases cover the mirror-image scenarios for
inserts and deletes on both axes.

```rust ! lib.rs
/// Returns a column's name from its number.
#[wasm_bindgen]
pub fn column_name(n: f64) -> String {
    util::column_name(n.floor() as i64)
}
/// Returns a column number from a name, or `null` if it is invalid or out of range.
#[wasm_bindgen]
pub fn column_from_name(s: &str) -> Option<f64> {
    Some(util::column_from_name(s)? as f64)
}

// ...

    #[test]
    fn test_relocate_formula() {
        // fill down by one row: relative refs follow, absolute stays
        // !mark(1:4)
        assert_eq!(
            "SUM(B3:C3) + $B$0",
            relocate_formula("SUM(B2:C2) + $B$0", 5.0, 2.0, 5.0, 3.0)
        );
        // fill right by two columns
        assert_eq!(
            "D0 * $A2",
            relocate_formula("B0 * $A2", 3.0, 2.0, 5.0, 2.0)
        );
        // mixed absolute column, relative row
        assert_eq!(
            "$B3",
            relocate_formula("$B1", 0.0, 1.0, 4.0, 3.0)
        );
    }
```
