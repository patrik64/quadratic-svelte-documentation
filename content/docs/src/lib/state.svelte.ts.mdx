The largest file in the project, and the hinge everything turns on. It holds
two things that could have been separate: the reactive UI state, and the
functions that mutate the document.

Keeping them together is what makes the app's structure work — a keyboard
shortcut, a menu entry and a context-menu item all call the same exported
function, so behavior lives in one place and the three entry points stay thin.

## !!steps A store built from runes, exposed through accessors

`createState` declares each piece as a `$state` rune inside a closure and
returns an object of getters and setters. That is the standard Svelte 5 pattern
for a module-level store: runes cannot be exported directly, but an object
whose properties read them can be.

The state splits into four groups — interaction (cursor, selection, whether the
cell input is open), editor and dialog visibility, user settings, and the
viewport.

The theme initializer is the one piece of logic here, reading `localStorage`
and applying `data-theme` to the document immediately so there is no flash of
the wrong theme. Note it defaults to `'light'` with no `prefers-color-scheme`
check, despite what the comment in [app.css](/docs/src/app.css) claims.

```ts ! state.svelte.ts
function createState() {
	// ---- interaction state ----
	// !mark(1:3)
	let cursorPosition = $state<Coordinate>({ x: 0, y: 0 });
	let keyboardMovePosition = $state<Coordinate>({ x: 0, y: 0 });
	let multiCursor = $state<MultiCursor | undefined>(undefined);
	let showInput = $state(false);
	let inputInitialValue = $state('');
	let panMode = $state<PanMode>('disabled');
	// ...
	// ---- settings ----
	// light by default; dark only when the user chose it (View → Dark theme)
	const storedTheme =
		typeof localStorage !== 'undefined'
			? (localStorage.getItem('quadratic-theme') as 'light' | 'dark' | null)
			: null;
	// !mark
	let theme = $state<'light' | 'dark'>(storedTheme ?? 'light');
	if (typeof document !== 'undefined') document.documentElement.dataset.theme = theme;
```

## !!steps The counter that stands in for a reactive model

The spreadsheet itself — [Sheet.ts](/docs/src/lib/core/Sheet.ts) and its maps —
is deliberately *not* reactive. Wrapping thousands of cells in Svelte proxies
would cost far more than it returns.

`redraw` is the substitute: a single integer bumped by `markDirty` after any
non-reactive mutation. Components that need to react to sheet content read it —
the `void app.redraw` line that appears in
[BottomBar.svelte](/docs/src/lib/components/BottomBar.svelte),
[SearchBar.svelte](/docs/src/lib/components/SearchBar.svelte) and
[GridCanvas.svelte](/docs/src/lib/components/GridCanvas.svelte) — turning one
coarse signal into a dependency they can subscribe to.

It is deliberately coarse. Any change invalidates every reader, which is
acceptable because the expensive consumer, the canvas, redraws from dirty flags
of its own rather than from this.

```ts ! state.svelte.ts
	// bump to force canvas redraw after non-reactive sheet mutations
	// !mark
	let redraw = $state(0);
	// ...
		get redraw() {
			return redraw;
		},
		// !mark
		markDirty() {
			redraw++;
		}
	};
}

export const app = createState();
```

## !!steps One hook wires the model to the UI and the disk

`onChange` on the controller is assigned exactly once, here, and it does both
jobs that must follow any mutation: signal the UI, and persist.

The autosave is **debounced at 300ms** with a cleared timer, so typing a row of
values produces one write rather than one per cell — important because each
write serializes the entire document through
[gridFile.ts](/docs/src/lib/files/gridFile.ts).

The outcome is fed back into the store. A success clears `saveError`, a failure
records it, and [BottomBar.svelte](/docs/src/lib/components/BottomBar.svelte)
surfaces that in the status bar — the only way a user would learn that their
work has stopped being saved.

```ts ! state.svelte.ts
// persist + redraw on any model change
let saveTimer: ReturnType<typeof setTimeout> | undefined;
sheetController.onChange = () => {
	app.markDirty();
	// !mark(1:2)
	clearTimeout(saveTimer);
	saveTimer = setTimeout(() => {
		void saveCurrentFile(exportGridFile(sheetController, app.filename, app.fileId))
			.then(() => (app.saveError = ''))
			.catch((e) => {
				// !mark
				app.saveError = String(e);
				console.error('autosave failed:', e);
			});
	}, 300);
};
```

## !!steps Selection as a rectangle, always

`getSelectionRect` is called by nearly every action in the file, and its value
is that it erases a distinction callers would otherwise repeat.

When a range is selected it normalizes the two corners; when only a cursor
exists it returns a one-cell rectangle. So `setBorders`, `copySelection`,
`deleteColumns` and the rest are written once against a rectangle, and the
single-cell case needs no branch anywhere.

This is why commands like "Delete row(s)" work identically whether you selected
a block or just placed the cursor.

```ts ! state.svelte.ts
export function getSelectionRect(): { x0: number; y0: number; x1: number; y1: number } {
	if (app.multiCursor) {
		const { originPosition: o, terminalPosition: t } = app.multiCursor;
		return {
			// !mark(1:4)
			x0: Math.min(o.x, t.x),
			y0: Math.min(o.y, t.y),
			x1: Math.max(o.x, t.x),
			y1: Math.max(o.y, t.y)
		};
	}
	const c = app.cursorPosition;
	// !mark
	return { x0: c.x, y0: c.y, x1: c.x, y1: c.y };
}
```

## !!steps Committing a value, or deleting by emptiness

`commitCellValue` is what the floating editor calls on close, and it treats an
empty string as a deletion rather than as a value — matching the spreadsheet
convention that clearing a cell removes it.

Both paths run through
[updateCellAndDCells.ts](/docs/src/lib/core/updateCellAndDCells.ts), so writing
a value and clearing one both trigger the same dependent recomputation. The
whole thing is wrapped in one transaction, which is why a commit that cascades
into ten recalculated cells still undoes in a single step.

The trailing autofit call handles wrapped text: a longer value in a wrapping
cell grows its row, and doing it inside the open transaction means the resize
undoes together with the edit.

```ts ! state.svelte.ts
export async function commitCellValue(x: number, y: number, value: string): Promise<void> {
	const sheet = sheetController.sheet;
	sheetController.startTransaction();
	// !mark
	if (value.trim() === '') {
		const existing = sheet.getCell(x, y);
		if (existing) {
			await updateCellAndDCells({
				starting_cells: [existing],
				sheetController,
				// !mark
				delete_starting_cells: true
			});
		}
	} else {
		const cell: Cell = {
			x,
			y,
			type: 'TEXT',
			value: value.trim(),
			last_modified: new Date().toISOString()
		};
		await updateCellAndDCells({ starting_cells: [cell], sheetController });
		if (sheet.getFormat(x, y)?.wrapping === 'wrap') autofitWrappedRows(x, y, x, y);
	}
	sheetController.endTransaction();
}
```

## !!steps Undo rebuilds the graph it cannot restore

Undo and redo delegate to the controller and then do one extra thing:
rebuild the dependency graph.

That is necessary because the transaction system reverses *cells*, not the
index derived from them. Restoring a cell restores its `evaluation_result` and
therefore its recorded reads, so the graph can be regenerated — which is
cheaper and more reliable than trying to capture and invert graph edges as part
of every operation.

It is the practical payoff of treating that graph as a discardable cache, as
described on [Sheet.ts](/docs/src/lib/core/Sheet.ts).

```ts ! state.svelte.ts
export function undo(): void {
	sheetController.undo();
	// !mark
	sheetController.sheet.rebuildDependencies();
}
```

## !!steps A format painter that clears as well as paints

The format painter stores a two-dimensional snapshot, deep-copied so later
edits to the source cannot change what is pasted.

The doc comment explains the choice that makes it a painter rather than a
merge: an `undefined` entry means "explicitly unformatted", and pasting it
**clears** the target's format. Copying a plain cell and painting it over a
bold one removes the bold, which is what a format painter is supposed to do —
a merge would leave it.

Pasting tiles the pattern with modulo indexing, so a 2×2 pattern painted over a
6×6 selection repeats. And because the span is the larger of pattern and
selection, painting into a single cell still lays down the whole pattern —
stated in the comment as Excel behavior.

```ts ! state.svelte.ts
export function pasteFormat(): void {
	if (!copiedFormats) return;
	const { x0, y0, x1, y1 } = getSelectionRect();
	const { w, h, formats } = copiedFormats;
	// !mark(1:2)
	const spanX = Math.max(x1 - x0 + 1, w);
	const spanY = Math.max(y1 - y0 + 1, h);
	sheetController.startTransaction();
	for (let dy = 0; dy < spanY; dy++) {
		for (let dx = 0; dx < spanX; dx++) {
			// !mark
			const src = formats[dy % h][dx % w];
			const x = x0 + dx;
			const y = y0 + dy;
			sheetController.execute({
				type: 'setFormat',
				x,
				y,
				format: src ? { ...(JSON.parse(JSON.stringify(src)) as CellFormat), x, y } : undefined
			});
		}
	}
	sheetController.endTransaction();
}
```

## !!steps Borders owned per cell, edges stored once

Borders are stored on each cell's four edges rather than as lines between
cells, which raises a question the comment answers: an interior border is
shared by two cells, so which one owns it?

The rule is that `inner` writes `top` on every row *after* the first and `left`
on every column after the first. Each shared edge therefore has exactly one
owner, so toggling borders cannot leave a duplicate behind, and clearing one
cell's border genuinely removes that line.

The `clear` branch shows the sparse discipline again: after deleting the
borders it checks whether anything is left, and passes `undefined` when the
format has become empty — deleting the record rather than storing a husk.

```ts ! state.svelte.ts
			const edges: CellBorders = { ...(format.borders ?? {}) };
			// !mark(1:2)
			if (mode === 'all' || ((mode === 'outer' || mode === 'top') && y === y0) || (mode === 'inner' && y > y0))
				edges.top = color;
			if (mode === 'all' || ((mode === 'outer' || mode === 'bottom') && y === y1)) edges.bottom = color;
			if (mode === 'all' || ((mode === 'outer' || mode === 'left') && x === x0) || (mode === 'inner' && x > x0))
				edges.left = color;
			if (mode === 'all' || ((mode === 'outer' || mode === 'right') && x === x1)) edges.right = color;
			if (Object.keys(edges).length === 0) continue;
			format.borders = edges;
			sheetController.execute({ type: 'setFormat', x, y, format });
```

## !!steps Clipboard as plain TSV

Copying builds tab-separated rows from raw cell values — not formatted display
values — so a number formatted as currency copies as `1234.5`, which is what
pastes usefully into another application.

Pasting reverses it, splitting on newlines and tabs and skipping empty fields
so a sparse block does not create empty cells. Both wrap their clipboard access
in `try`/`catch`, because the Clipboard API rejects without permission and a
denied read should do nothing rather than throw.

Cut is composed rather than special-cased: copy, then delete the same
rectangle. Only the deletion is a mutation, and `deleteCellsInRect` wraps it in
its own transaction — so a cut is still a single undo step.

```ts ! state.svelte.ts
export async function copySelection(cut = false): Promise<void> {
	const { x0, y0, x1, y1 } = getSelectionRect();
	const sheet = sheetController.sheet;
	const lines: string[] = [];
	for (let y = y0; y <= y1; y++) {
		const parts: string[] = [];
		// !mark
		for (let x = x0; x <= x1; x++) parts.push(sheet.getCell(x, y)?.value ?? '');
		lines.push(parts.join('\t'));
	}
	try {
		await navigator.clipboard.writeText(lines.join('\n'));
	} catch {
		// clipboard permission denied; ignore
	}
	// !mark
	if (cut) await deleteCellsInRect(x0, y0, x1, y1);
}
```

## !!steps Zoom anchored on a point

`setZoom` clamps to a 0.1–10 range and then does anchored zooming: convert the
anchor to world coordinates *before* changing scale, and afterwards place the
viewport so that same world point sits back under the anchor.

Defaulting the anchor to the canvas centre is what makes the zoom buttons and
`⌘+` feel right — they magnify what you are looking at rather than drifting
toward the origin. The identical arithmetic appears in
[PixiGrid.ts](/docs/src/lib/grid/pixi/PixiGrid.ts) for cmd+wheel, anchored on
the pointer instead.

`zoomToRect` inverts the relationship, solving for the scale that fits a
rectangle with a 1.2 buffer and capping at 2 so zooming to a single small cell
does not fill the screen with one number.

```ts ! state.svelte.ts
export function setZoom(scale: number, centerScreen?: { x: number; y: number }): void {
	// !mark
	const clamped = Math.min(10, Math.max(0.1, scale));
	const canvas = document.querySelector<HTMLCanvasElement>('canvas.grid-canvas');
	const center = centerScreen ?? {
		x: (canvas?.clientWidth ?? window.innerWidth) / 2,
		y: (canvas?.clientHeight ?? window.innerHeight) / 2
	};
	// !mark(1:3)
	const world = screenToWorld(center.x, center.y);
	app.viewport = {
		scale: clamped,
		x: world.x - center.x / clamped,
		y: world.y - center.y / clamped
	};
}
```

## !!steps Inserting a row without re-running the sheet

`shiftAxis` is the most involved function in the file, and its doc comment
records a decision that is easy to get wrong: inserting a row **does not re-run
code cells**.

The reason is stated plainly — re-running could regenerate random data or
re-spill over the sheet. So instead of recomputing, the shift carries each
cell's *metadata* along: `array_cells` and `cells_accessed` are remapped so the
dependency graph and spill blocks stay consistent with the new positions.

Formulas are the exception, because their A1 text encodes positions that must
follow the shift; they are rewritten through the Rust core's `adjust_formula`.
Python and JavaScript reference strings are left alone, since those are
arbitrary code rather than a parseable reference syntax — a real asymmetry the
comment is honest about.

The sort direction matters: shifting away from the origin processes cells in
descending order so a move never overwrites a cell not yet processed.

```ts ! state.svelte.ts
	const cells = sheet
		.getAllCells()
		// !mark
		.sort((a, b) => (desc ? b[axis] - a[axis] : a[axis] - b[axis]));
	for (const cell of cells) {
		const movedCoord = cell[axis] >= at;
		// !mark(1:2)
		const array_cells = cell.array_cells?.map(shiftPair);
		const cells_accessed = cell.evaluation_result?.cells_accessed?.map(shiftPair);
		// formulas follow the shift: their A1 text is rewritten by the core
		let formula_code = cell.formula_code;
		if (cell.type === 'FORMULA' && formula_code && adjustFormula) {
			formula_code = await adjustFormula(formula_code, cell, axis, at, delta);
```

## !!steps Opening a file, from three sources

The three open paths — a new blank file, a file from disk or an example, and a
stored file — converge on the same sequence: import, rebuild cross-sheet
dependencies, reset filename and id, move the cursor home, fire `onChange`,
and fit the view.

`rebuildCrossSheetDeps` has to run explicitly because those dependencies are
not persisted; they are re-derived by scanning formula text, as described on
[SheetController.ts](/docs/src/lib/core/SheetController.ts).

Firing `onChange` is what makes the opened file become the *current* one — the
autosave it triggers writes both the document and the pointer, so a reload
returns to it. `zoomToFit` then frames the content, which is why opening an
example lands on the data rather than at the origin.

```ts ! state.svelte.ts
export async function openStoredFile(id: string): Promise<void> {
	const file = await loadStoredFile(id);
	if (!file) return;
	importGridFile(sheetController, file);
	// !mark
	sheetController.rebuildCrossSheetDeps(findSheetRefs);
	app.filename = file.filename ?? DEFAULT_FILE_NAME;
	app.fileId = file.id ?? crypto.randomUUID();
	app.cursorPosition = { x: 0, y: 0 };
	app.multiCursor = undefined;
	// !mark
	sheetController.onChange(); // autosave re-persists it as the current file
	zoomToFit();
}
```

Nearly every exported function follows the same shape: read
`getSelectionRect`, open a transaction, execute ops or call
[updateCellAndDCells.ts](/docs/src/lib/core/updateCellAndDCells.ts), close the
transaction. That uniformity is what makes a paste of fifty cells or a fill of
a hundred a single undo step.

The consumers are the three entry points into the app —
[keyboard.ts](/docs/src/lib/grid/keyboard.ts),
[CommandPalette.svelte](/docs/src/lib/components/CommandPalette.svelte) and
[GridContextMenu.svelte](/docs/src/lib/components/GridContextMenu.svelte) —
plus the components that read state directly. Because all three import from
here rather than reimplementing, a behavior fixed once is fixed everywhere.

One structural note: `pixiRef` is a mutable box assigned by
[GridCanvas.svelte](/docs/src/lib/components/GridCanvas.svelte), giving actions
like PNG export a way to reach the renderer. It is the one place the store
depends on the view rather than the other way round.
