Two small tokenizers, written by hand rather than pulled from a library. They
power the code editor's highlighting and the cell hover card, and they are
built around one unusual constraint: **the concatenated text of the tokens must
equal the input exactly**.

That constraint comes from how the editor works. A highlighted `<pre>` sits
underneath a transparent `<textarea>`, and the two only stay aligned if the
rendered text is glyph-for-glyph identical to what was typed. A tokenizer that
normalized whitespace, dropped a stray character, or skipped an unterminated
string would desynchronize the caret from the text under it.

## !!steps Six token types and an escape hatch

The type union is deliberately small — these classes map onto the `syn-*` CSS
rules in [app.css](/docs/src/app.css), and every additional class would need a
color in both themes.

`plain` is what makes the round-trip guarantee achievable: anything the
tokenizer does not recognize is still emitted, just unstyled. There is no
"unknown" failure mode and nothing is ever discarded.

The header comment is candid about the limits. JavaScript regex literals are
not recognized at all, because telling `/foo/` from division requires knowing
whether the previous token was a value — that is a parser's job, not a
scanner's — so they render as plain text. Python f-string interpolations stay
inside the string rather than being tokenized as code.

```ts ! codeHighlight.ts
export type CodeTokenType =
	| 'keyword'
	| 'literal'
	| 'string'
	| 'number'
	| 'comment'
	| 'function'
	// !mark
	| 'plain';

export interface CodeToken {
	type: CodeTokenType;
	text: string;
}
```

## !!steps Three languages, two tokenizers

Formula cells reuse the JavaScript tokenizer. The doc comment justifies it
rather than hiding it: formulas are mostly strings, numbers and call-shaped
identifiers, all of which the JS scanner already classifies correctly. A
dedicated formula tokenizer would add a third code path for very little visible
gain.

The consequence is that a formula's function names light up because they are
followed by `(`, not because the tokenizer knows anything about the function
library in [functions/mod.rs](/docs/quadratic-core/src/formulas/functions/mod.rs).

```ts ! codeHighlight.ts
/** Picks the tokenizer for a code cell / editor language. Formulas reuse the
 * JS tokenizer: strings, numbers, and call-shaped identifiers cover formula
 * syntax well. */
export function tokenizeCode(
	lang: 'FORMULA' | 'PYTHON' | 'JAVASCRIPT',
	code: string
): CodeToken[] {
	// !mark
	return lang === 'PYTHON' ? tokenizePython(code) : tokenizeJs(code);
}
```

## !!steps Coalescing the unstyled runs

Both tokenizers emit plain characters one at a time as they fall through their
recognizers. Left alone that would produce a token per space and per operator —
and since each token becomes a DOM node in the rendered `<pre>`, a 200-line
cell would generate thousands of `span` elements.

`TokenSink` buffers consecutive plain text and only materializes it when a
typed token interrupts it, so `x = y + 1` yields a handful of nodes rather than
a dozen. Every path that emits a typed token calls `flush` first, which is what
keeps the output in source order. `done` flushes the tail.

```ts ! codeHighlight.ts
class TokenSink {
	tokens: CodeToken[] = [];
	private plain = '';

	flush(): void {
		if (this.plain) {
			this.tokens.push({ type: 'plain', text: this.plain });
			this.plain = '';
		}
	}
	push(type: CodeTokenType, text: string): void {
		if (!text) return;
		// !mark
		this.flush();
		this.tokens.push({ type, text });
	}
	pushPlain(text: string): void {
		this.plain += text;
	}
	pushAll(tokens: CodeToken[]): void {
		this.flush();
		this.tokens.push(...tokens);
	}
	done(): CodeToken[] {
		this.flush();
		return this.tokens;
	}
}
```

## !!steps Comments and strings that never run away

Both comment forms clamp to the end of input when unterminated: a `//` with no
newline takes `j = n`, and an unclosed `/*` does the same. Neither can index
past the end, and both consume every character they saw — the round-trip
guarantee holding at the edges.

The string scanner steps over a backslash and the character after it, which is
how `'it\'s'` stays one token. The second stop condition is the interesting
one: a newline ends the string even without a closing quote. That is not how
JavaScript actually parses — an unterminated string is a syntax error — but it
is the right behavior for a *live editor*, where a half-typed string would
otherwise paint the rest of the file as a string until the closing quote
arrives.

```ts ! codeHighlight.ts
		if (ch === '/' && next === '*') {
			const end = code.indexOf('*/', i + 2);
			// !mark
			const j = end === -1 ? n : end + 2;
			out.push('comment', code.slice(i, j));
			i = j;
			continue;
		}

		// single/double-quoted string; unterminated ones stop at the newline
		if (ch === '"' || ch === "'") {
			let j = i + 1;
			while (j < n && code[j] !== ch && code[j] !== '\n') {
				if (code[j] === '\\') j++;
				j++;
			}
			if (j < n && code[j] === ch) j++;
			out.push('string', code.slice(i, j));
			i = j;
			continue;
		}
```

## !!steps Template literals, tokenized recursively

The most involved branch, because a template literal is a string containing
code containing possibly more strings.

When `${` appears, the string segment so far is emitted, the delimiter is
pushed as plain, and the interpolation's extent is found by counting braces.
Its contents are then handed to **`tokenizeJs` recursively**, so `${x + 1}`
highlights its number and identifiers exactly as it would outside the template
— and nesting works to any depth for free.

The comment is honest about where this breaks: the depth count does not know
about strings, so a `}` inside a nested string ends the interpolation early.
The `closed` flag is what keeps that harmless — when the braces never balance,
the closing `}` is not emitted and `k` has run to the end, so the remaining
text is still consumed and the round trip survives. Highlighting degrades;
alignment does not.

```ts ! codeHighlight.ts
				if (c === '$' && code[j + 1] === '{') {
					out.push('string', code.slice(seg, j));
					out.push('plain', '${');
					let depth = 1;
					let k = j + 2;
					// !mark(1:5)
					while (k < n && depth > 0) {
						if (code[k] === '{') depth++;
						else if (code[k] === '}') depth--;
						k++;
					}
					const closed = depth === 0;
					out.pushAll(tokenizeJs(code.slice(j + 2, closed ? k - 1 : k)));
					if (closed) out.push('plain', '}');
					j = k;
					seg = j;
					continue;
				}
```

## !!steps Two lookarounds decide what a word is

Identifiers are classified by looking at their neighbours, and both checks skip
inline whitespace via `skipInlineSpace` so spacing does not change the answer.

`afterDot` prevents property names from being painted as keywords — `a.new` and
`q.delete` are ordinary members, and highlighting them as syntax would be
actively misleading. It gates both the keyword and literal branches.

`isCall` is the function heuristic: an identifier followed by `(` is styled as
a call. It is a heuristic rather than analysis — no declaration is consulted —
but it costs one character of lookahead and catches essentially every call
users write, including the `q.cells(...)` and `cell(...)` API.

Anything left over goes to `pushPlain`, joining the buffered run rather than
becoming its own node.

```ts ! codeHighlight.ts
		if (JS_IDENT_START.test(ch)) {
			let j = i + 1;
			while (j < n && JS_IDENT_PART.test(code[j])) j++;
			const word = code.slice(i, j);
			// dotted property access is never a keyword: `a.new`, `q.delete`
			// !mark(1:2)
			const afterDot = code[skipInlineSpace(code, i - 1, -1)] === '.';
			const isCall = code[skipInlineSpace(code, j, 1)] === '(';
			if (!afterDot && JS_KEYWORDS.has(word)) out.push('keyword', word);
			else if (!afterDot && JS_LITERALS.has(word)) out.push('literal', word);
			else if (isCall) out.push('function', word);
			else out.pushPlain(word);
			i = j;
			continue;
		}
```

## !!steps Numbers, in both languages

Each language gets one alternation-heavy regex anchored at the current
position, covering hex, binary and octal prefixes, decimals with optional
exponents, and a leading-dot form like `.25`.

The tails differ by language and are the giveaway that these were written
separately: JavaScript allows a `n` suffix for BigInt, while Python allows `j`
for imaginary numbers and — the easily-forgotten one — underscores as digit
separators, so `1_000` must scan as a single number rather than a number
followed by an identifier.

Both are only attempted when the current character is a digit, or a dot
followed by one, so the regex never runs against arbitrary text.

```ts ! codeHighlight.ts
const JS_NUMBER =
	/^(?:0[xX][0-9a-fA-F]+n?|0[bB][01]+n?|0[oO][0-7]+n?|\d+(?:\.\d*)?(?:[eE][+-]?\d+)?n?|\.\d+(?:[eE][+-]?\d+)?)/;
// ...
const PY_NUMBER =
	// !mark
	/^(?:0[xX][0-9a-fA-F_]+|0[bB][01_]+|0[oO][0-7_]+|\d[\d_]*(?:\.[\d_]*)?(?:[eE][+-]?\d+)?[jJ]?|\.\d[\d_]*(?:[eE][+-]?\d+)?[jJ]?)/;
```

## !!steps Python strings, including the triple-quoted kind

Python's string rules need their own scanner because a `'''` or `"""` string
spans lines, while a single-quoted one must still stop at a newline for the
same live-editing reason as JavaScript.

`triple` is decided once by peeking three characters, and the loop then applies
whichever termination rule fits — a matching triple for one, a quote or newline
for the other. Escapes skip two characters in both. Every path returns an index
inside the input, and running off the end returns `n`, so the caller always
consumes something and never loops forever.

```ts ! codeHighlight.ts
function scanPyString(code: string, quoteAt: number): number {
	const n = code.length;
	const q = code[quoteAt];
	// !mark
	const triple = code.slice(quoteAt, quoteAt + 3) === q + q + q;
	let j = quoteAt + (triple ? 3 : 1);
	while (j < n) {
		const c = code[j];
		if (c === '\\') {
			j += 2;
			continue;
		}
		if (triple) {
			if (c === q && code.slice(j, j + 3) === q + q + q) return j + 3;
		} else {
			if (c === q) return j + 1;
			if (c === '\n') return j;
		}
		j++;
	}
	return n;
}
```

## !!steps Prefixed strings, caught in the identifier branch

`f'...'`, `rb"..."` and friends begin with what looks like an identifier, so
they are handled where identifiers are handled rather than in the string
branch.

Once a word is scanned, the check is whether a quote follows *immediately* and
the word matches one or two prefix letters. If so the whole thing — prefix and
string together — is emitted as a single string token, which is why an f-string
appears entirely as a string rather than a stray `f` followed by one.

The one-or-two-character bound is what stops an ordinary identifier that
happens to precede a quote from being swallowed; a longer word is left alone
and the quote is scanned separately on the next pass.

```ts ! codeHighlight.ts
		if (PY_IDENT_START.test(ch)) {
			let j = i + 1;
			while (j < n && PY_IDENT_PART.test(code[j])) j++;
			const word = code.slice(i, j);
			// string prefix: f'…', rb"…", …
			// !mark(1:2)
			if ((code[j] === '"' || code[j] === "'") && /^[rbufRBUF]{1,2}$/.test(word)) {
				const end = scanPyString(code, j);
				out.push('string', code.slice(i, end));
				i = end;
				continue;
			}
			const afterDot = code[skipInlineSpace(code, i - 1, -1)] === '.';
			const isCall = code[skipInlineSpace(code, j, 1)] === '(';
			if (!afterDot && PY_KEYWORDS.has(word)) out.push('keyword', word);
			else if (!afterDot && PY_LITERALS.has(word)) out.push('literal', word);
			else if (isCall) out.push('function', word);
			else out.pushPlain(word);
			i = j;
			continue;
		}
```

The tokens are rendered as `span` elements carrying `syn-{type}` classes by
[CodeEditor.svelte](/docs/src/lib/components/CodeEditor.svelte) — the overlay
whose alignment depends on the round-trip guarantee — and by the cell hover card
in [GridCanvas.svelte](/docs/src/lib/components/GridCanvas.svelte). Because
those class names are built at runtime, their colors have to live in the global
[app.css](/docs/src/app.css) rather than in either component.

The round-trip property is asserted directly, for both languages and including
unterminated input, in
[codeHighlight.test.ts](/docs/src/lib/helpers/codeHighlight.test.ts).
