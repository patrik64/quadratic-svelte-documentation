The grid itself is drawn by PixiJS, which knows nothing about Svelte. This
component is the seam between them: it creates and owns the engine, feeds it a
snapshot of the reactive UI state, and translates raw pointer events into the
gestures a spreadsheet needs — select, drag-select, fill, resize columns and
rows, point at cells while writing a formula.

That last part is the bulk of the file. A single `pointerdown` can mean six
different things depending on where it lands and what is open, and the ordering
of those checks is the component's real design.

## !!steps A snapshot instead of a subscription

`snapshot()` gathers everything the renderer needs into one plain object. The
engine calls it each frame rather than subscribing to anything, which keeps
[PixiGrid.ts](/docs/src/lib/grid/pixi/PixiGrid.ts) free of any Svelte
dependency — it just asks for the current state.

Reading every field also serves a second purpose used below: calling
`snapshot()` inside an effect registers a dependency on all of them at once.

Note the last two entries are **local** component state, not store state. The
fill and reference previews exist only while a drag is in progress, so they live
here and reach the renderer through the same channel as everything else.

```svelte ! GridCanvas.svelte
<script lang="ts">
	function snapshot(): GridUIState {
		return {
			cursorPosition: app.cursorPosition,
			multiCursor: app.multiCursor,
			showHeadings: app.showHeadings,
			// ...
			inputOpen: app.showInput,
			// !mark(1:2)
			fillPreview,
			refPreview
		};
	}
</script>
```

## !!steps Creating and tearing down the engine

`onMount` builds the `PixiGrid`, handing it two accessors — the current sheet
and the snapshot function — so the engine pulls rather than being pushed to.

Initialization is async, and `disposed` guards the callback: if the component
unmounts before WebGL finishes setting up, the continuation returns instead of
configuring a destroyed engine. The `ResizeObserver` is created inside that
callback for the same reason.

The camera link is established here too, and it runs both ways — `onViewportChanged`
writes pans and zooms into the store, while `applyViewport` pushes the stored
position back in. The epsilon guard inside `applyViewport` is what stops those
two directions from oscillating.

The returned cleanup removes all three listeners and destroys the engine,
releasing GPU resources that garbage collection would not reclaim.

```svelte ! GridCanvas.svelte
<script lang="ts">
	onMount(() => {
		const grid = new PixiGrid(() => sheetController.sheet, snapshot);
		pixi = grid;
		pixiRef.current = grid;
		let disposed = false;
		let observer: ResizeObserver | undefined;

		void grid.init(containerEl!).then(() => {
			// !mark
			if (disposed) return;
			// pixi viewport is the source of truth while the user pans/zooms
			grid.onViewportChanged = (x, y, scale) => {
				app.viewport = { x, y, scale };
			};
			grid.applyViewport(app.viewport.x, app.viewport.y, app.viewport.scale);
			grid.setTheme(app.theme);
			observer = new ResizeObserver(() => {
				if (containerEl) grid.resize(containerEl.clientWidth, containerEl.clientHeight);
			});
			observer.observe(containerEl!);
		});
</script>
```

## !!steps Translating reactivity into dirty flags

Three effects convert Svelte's change notifications into the engine's dirty
flags. The first watches the redraw counter that signals a non-reactive sheet
mutation and marks the cells dirty.

The second is the clever one. Calling `snapshot()` registers a dependency on
*every* UI field at once, so any of them re-runs this effect — but not all of
them cost the same to redraw. Cursor movement needs only the overlay repainted,
whereas toggling gridlines or headings changes the whole scene. So the settings
are joined into a string and compared with the previous one, and the expensive
`dirtyViewport` flag is raised only when something structural actually changed.

The third pushes externally-driven camera moves — zoom buttons, go-to, keyboard
scrolling — down into the viewport.

```svelte ! GridCanvas.svelte
<script lang="ts">
	let lastSettings = '';
	$effect(() => {
		const s = snapshot(); // registers all UI-state dependencies
		const settings = `${s.showHeadings}|${s.showGridAxes}|${s.showGridLines}|${s.showCellTypeOutlines}|${s.showA1Notation}|${s.presentationMode}`;
		if (pixi) {
			pixi.dirtyCursor = true;
			// !mark
			if (settings !== lastSettings) pixi.dirtyViewport = true; // lines/outlines/headings visibility
		}
		lastSettings = settings;
	});
</script>
```

## !!steps One key that must always get through

Presentation mode hides every control, so Escape is the only way out — and by
then a modal, the cell input or the code editor may be focused, all of which
stop propagation of bubbled keys.

Registering this listener in the **capture** phase gets ahead of all of them:
capture runs from the window down toward the target, so this handler sees the
event before any component can swallow it. It acts only in presentation mode,
leaving Escape to behave normally everywhere else.

The space bar handler shows the opposite concern. Space toggles pan mode, but
only outside a text field, where it is an ordinary character. `preventDefault`
stops the page scrolling, and the comment records that `pixi-viewport`'s drag
plugin watches the key itself — so this only manages the app's own pan state.

```svelte ! GridCanvas.svelte
<script lang="ts">
	// capture phase so Esc exits presentation mode even when a component
	// (code editor, modal, cell input) stops propagation of bubbled keys
	function onWindowKeyDownCapture(e: KeyboardEvent): void {
		// !mark
		if (e.key === 'Escape' && app.presentationMode) {
			app.presentationMode = false;
			e.preventDefault();
			e.stopPropagation();
		}
	}

	function onWindowKeyDown(e: KeyboardEvent): void {
		const target = e.target as HTMLElement;
		const inField =
			target instanceof HTMLInputElement ||
			target instanceof HTMLTextAreaElement ||
			target?.isContentEditable;
		// !mark
		if (e.key === ' ' && !inField && !app.showInput) {
			spaceHeld = true;
			if (app.panMode === 'disabled') app.panMode = 'enabled';
			e.preventDefault(); // pixi-viewport's drag plugin tracks the key itself
			return;
		}
		handleKeyDown(e);
	}
</script>
```

## !!steps Hit-testing in screen space

Turning a pointer position into a grid location goes through
[GridOffsets.ts](/docs/src/lib/core/GridOffsets.ts) — screen to world, then
world to column and row indices, so the DOM layer and the renderer agree
exactly on which cell is where.

The fill handle test converts the other way, projecting the selection's
bottom-right corner into screen space and accepting anything within six pixels.
Doing it in screen space rather than world space is deliberate: the handle stays
the same physical size at every zoom level, so the grab area has to be measured
in pixels too.

`hitHeadingEdge` uses the same approach with a four-pixel tolerance, checking
both the edge of the column under the pointer and the next one so the boundary
is grabbable from either side. It reports `index - 1`, since dragging an edge
resizes the column to its *left*.

```svelte ! GridCanvas.svelte
<script lang="ts">
	/** True when the screen point is over the fill handle (selection corner). */
	function hitFillHandle(sx: number, sy: number): boolean {
		const sel = getSelectionRect();
		const offsets = sheetController.sheet.gridOffsets;
		const rect = offsets.getCellRect(sel.x1, sel.y1);
		const hx = (rect.x + rect.w - app.viewport.x) * app.viewport.scale;
		const hy = (rect.y + rect.h - app.viewport.y) * app.viewport.scale;
		// !mark
		return Math.abs(sx - hx) <= 6 && Math.abs(sy - hy) <= 6;
	}
</script>
```

## !!steps Six meanings for one press, in priority order

`onPointerDown` is a cascade, and the order encodes which gesture wins when two
are possible.

Pan mode comes first and returns immediately, handing the drag to
`pixi-viewport`. Then the fill handle, checked before anything else on the grid
because it sits *on top of* a cell — testing the cell first would make the
handle unreachable. Heading edges come before heading bodies for the same
reason: the resize zone overlaps the header you would otherwise be clicking to
select.

`setPointerCapture` appears in every branch that starts a drag. It routes
subsequent pointer events to this element even when the pointer leaves it, so
dragging a selection past the window edge keeps working instead of silently
stopping.

```svelte ! GridCanvas.svelte
<script lang="ts">
		// fill-handle drag
		// !mark
		if (!app.showInput && hitFillHandle(sx, sy)) {
			containerEl.setPointerCapture(e.pointerId);
			fillSource = getSelectionRect();
			fillPreview = { ...fillSource };
			dragMode = 'fill';
			return;
		}

		// heading interactions
		const edge = hitHeadingEdge(sx, sy);
		if (edge) {
			containerEl.setPointerCapture(e.pointerId);
			const offsets = sheetController.sheet.gridOffsets;
			if (edge.kind === 'col') {
				dragMode = 'col-resize';
				resizeTarget = {
					index: edge.index,
					originalSize: offsets.getColumnWidth(edge.index),
					startWorld: screenToWorld(sx, sy).x
				};
			}
			return;
		}
</script>
```

## !!steps When a click means a reference, not a selection

With a formula open, clicking the grid does something different: it inserts the
clicked cell's reference into the editor rather than moving the cursor. This is
the pointing mode every spreadsheet has, and it is checked before the ordinary
selection branch so it takes precedence.

`!e.shiftKey` is the escape hatch — shift-clicking still selects normally, so
the grid remains navigable while an editor is open.

The reference is sent immediately on press, then re-sent on every drag that
changes the cell, which is how dragging out a range updates the formula live.
That works because [CodeEditor.svelte](/docs/src/lib/components/CodeEditor.svelte)
remembers where the last reference landed and **replaces** it rather than
appending — the `lastRefSpan` mechanism on that page.

```svelte ! GridCanvas.svelte
<script lang="ts">
		// formula pointing mode: a grid click inserts the cell's reference
		// into the open formula editor instead of moving the cursor
		// !mark
		if (app.showCodeEditor && app.editorMode === 'FORMULA' && !e.shiftKey) {
			containerEl.setPointerCapture(e.pointerId);
			const pointed = cellAtScreen(sx, sy);
			refOrigin = pointed;
			refPointed = pointed;
			sendRefInsert(pointed, pointed);
			dragMode = 'ref';
			return;
		}
</script>
```

## !!steps Fill extends along one axis only

While dragging the fill handle, the preview grows in whichever direction the
pointer has travelled further — comparing the vertical and horizontal distance
past the selection's edge and committing to the larger.

Constraining it to a single axis matches how fill works everywhere: filling
down and right at once has no sensible meaning. The `dy >= dx` comparison
breaks ties toward vertical, which is the more common gesture.

Neither branch can shrink the source: both distances must be positive, and
dragging back inside the selection falls through to the `else`, restoring the
preview to the original rectangle.

```svelte ! GridCanvas.svelte
<script lang="ts">
		if (dragMode === 'fill' && fillSource) {
			const cell = cellAtScreen(sx, sy);
			// extend along the dominant axis only, never shrinking the source
			const dy = cell.y - fillSource.y1;
			const dx = cell.x - fillSource.x1;
			// !mark(1:6)
			if (dy >= dx && dy > 0) {
				fillPreview = { ...fillSource, y1: cell.y };
			} else if (dx > 0) {
				fillPreview = { ...fillSource, x1: cell.x };
			} else {
				fillPreview = { ...fillSource };
			}
			return;
		}
</script>
```

## !!steps Making a resize undoable after the fact

Resizing is the one gesture that has to be rewritten when it ends. During the
drag, each move writes straight into `GridOffsets` so the columns track the
pointer — fast, but invisible to the undo system, and it would otherwise record
dozens of intermediate widths.

So on release the final size is read back, the offsets are **reset to the
original**, and the change is replayed through a single transaction on
[SheetController.ts](/docs/src/lib/core/SheetController.ts). The user sees no
flicker because both happen in the same tick, and undo now has exactly one
operation to reverse: the whole resize.

The fill branch above it commits through `fillRange` and then selects the
result, so the newly filled cells are highlighted — matching what a spreadsheet
does after a fill.

```svelte ! GridCanvas.svelte
<script lang="ts">
		if (dragMode === 'col-resize' || dragMode === 'row-resize') {
			// re-apply through a transaction so resize is undoable
			const offsets = sheetController.sheet.gridOffsets;
			const kind = dragMode === 'col-resize' ? 'column' : 'row';
			const finalSize =
				kind === 'column'
					? offsets.getColumnWidth(resizeTarget.index)
					: offsets.getRowHeight(resizeTarget.index);
			// !mark(1:2)
			if (kind === 'column') offsets.setColumnWidth(resizeTarget.index, resizeTarget.originalSize);
			else offsets.setRowHeight(resizeTarget.index, resizeTarget.originalSize);
			sheetController.startTransaction();
			sheetController.execute({ type: 'setHeading', kind, id: resizeTarget.index, size: finalSize });
			sheetController.endTransaction();
		}
</script>
```

## !!steps Double-click, right-click, and dropped files

Double-clicking opens whatever the cell warrants — the code editor for a code
cell, the plain input otherwise — but returns early when a formula is being
edited, since pointing mode owns grid clicks and retargeting the editor
mid-formula would be wrong.

The context menu handler adds a rule worth knowing: right-clicking **outside**
the current selection moves the cursor there first, so the menu always acts on
what you right-clicked. Right-clicking inside a selection leaves it intact, so
a menu action applies to the whole block.

Dropping a file dispatches on extension — `.grid` and `.json` replace the whole
document, while a `.csv` imports **at the cell under the pointer**, so where you
drop determines where the data lands.

```svelte ! GridCanvas.svelte
<script lang="ts">
	async function onDrop(e: DragEvent): Promise<void> {
		e.preventDefault();
		const file = e.dataTransfer?.files?.[0];
		if (!file) return;
		const text = await file.text();
		if (file.name.endsWith('.grid') || file.name.endsWith('.json')) {
			openFileFromJSON(text, file.name);
		} else if (file.name.endsWith('.csv')) {
			const rect = containerEl?.getBoundingClientRect();
			// !mark(1:3)
			const at = rect
				? cellAtScreen(e.clientX - rect.left, e.clientY - rect.top)
				: app.cursorPosition;
			await importCSVAt(text, at);
		}
	}
</script>
```

## !!steps The DOM layers above the canvas

The container holds the canvas and every DOM element that has to sit over it:
the floating cell editor, the search bar, the context menu and the hover card.

They live here rather than in [+page.svelte](/docs/src/routes/+page.svelte)
because each is positioned in grid coordinates, and this element is their
positioning context. `role="application"` tells assistive technology this is an
interactive widget rather than a document, since none of the grid is real DOM.

The cursor is driven by a derived value rather than set imperatively, so pan
mode always wins over whatever hover styling the pointer-move handler last
computed.

```svelte ! GridCanvas.svelte
<div
	bind:this={containerEl}
	class="grid-container"
	style:cursor={containerCursor}
	role="application"
	aria-label="Spreadsheet grid"
	onpointerdown={onPointerDown}
	onpointermove={onPointerMove}
	onpointerup={onPointerUp}
	onpointerleave={clearHover}
	ondblclick={onDoubleClick}
	oncontextmenu={onContextMenu}
	ondragover={(e) => e.preventDefault()}
	ondrop={onDrop}
>
	{#if app.showInput}
		<CellInput />
	{/if}
```

## !!steps A hover card that stays on screen

Hovering a code or error cell shows a card with its source or error text, after
a delay tracked by `hoverTimer` and `hoverKey` so moving across cells does not
flash cards continuously.

Its position is computed to keep it inside the container: `left` is clamped so a
card near the right edge does not overflow, and `top` flips the card **above**
the pointer when there is not enough room below — the standard tooltip
behavior, done with one conditional.

The body reuses the tokenizer from
[codeHighlight.ts](/docs/src/lib/helpers/codeHighlight.ts), rendering the same
`syn-{type}` spans the code editor uses. That is the second consumer that makes
those classes global in [app.css](/docs/src/app.css), and it means a formula
looks identical whether you hover it or open it.

```svelte ! GridCanvas.svelte
	{#if hoverCard}
		{@const info = hoverInfo(hoverCard.cell)}
		<div
			class="hover-card"
			style:left="{Math.max(0, Math.min(hoverCard.sx + 14, (containerEl?.clientWidth ?? 400) - 330))}px"
			style:top="{hoverCard.sy + 190 > (containerEl?.clientHeight ?? 300)
				? hoverCard.sy - 160
				: hoverCard.sy + 18}px"
		>
			<div class="hc-head" style:color={info.color}>{info.label}</div>
			<pre class="hc-body">{#if info.tokens}{#each info.tokens as t}{#if t.type === 'plain'}{t.text}{:else}<span class="syn-{t.type}">{t.text}</span>{/if}{/each}{:else}{info.body}{/if}</pre>
		</div>
	{/if}
```

Almost every mutation here routes through
[state.svelte.ts](/docs/src/lib/state.svelte.ts) rather than touching the sheet
directly, so the same operations are reachable from
[keyboard.ts](/docs/src/lib/grid/keyboard.ts) and the command palette. The
exception is the live resize, which writes to
[GridOffsets.ts](/docs/src/lib/core/GridOffsets.ts) directly and then replays
itself as a transaction — the one place performance justified bypassing the
model, with the bypass corrected before it becomes permanent.
