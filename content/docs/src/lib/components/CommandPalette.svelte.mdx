The palette that opens on `⌘P`, listing every action the app can perform. Most
of the file is the list itself — 71 commands declared as data — and the
surrounding UI is deliberately thin: a search box, a filtered list, and arrow
keys.

Its real role is as an index of the application. Nearly every entry delegates
to a function already exported by
[state.svelte.ts](/docs/src/lib/state.svelte.ts), so the palette adds no
behavior of its own; it makes existing behavior findable.

<Scrollycoding>

## !!steps Commands as data

The `Command` shape is four fields, and one of them is worth noting: `group` is
set on every single entry and then **never read** — the markup renders only
`label` and `shortcut`, and filtering matches on `label` alone. It is
groundwork for grouped rendering that has not been built.

That is less of an omission than it looks, because of the labelling
convention below. `C` aliases the platform-aware Cmd glyph from
[keyboardSymbols.ts](/docs/src/lib/helpers/keyboardSymbols.ts) once, so the 30-odd
shortcut strings that interpolate it read tolerably.

```svelte ! CommandPalette.svelte
<script lang="ts">
	const C = KeyboardSymbols.Cmd;

	interface Command {
		// !mark
		group: string;
		label: string;
		shortcut?: string;
		action: () => void;
	}
</script>
```

## !!steps Labels that carry their own category

Every label repeats its group as a prefix — `File: New`, `Edit: Undo`,
`View: Zoom in`. That redundancy is what lets the filter stay a single
case-insensitive substring match while still behaving like a categorized menu:
typing `file` narrows to the File commands, `zoom` finds them across groups.

The actions show three shapes. Some are bare references to store functions,
which is the ideal case. Some wrap a call that needs arguments or `void` to
discard a promise. And a few toggle a flag inline — the view options are all of
that form, reading and writing the same property in one expression.

```svelte ! CommandPalette.svelte
<script lang="ts">
	const commands: Command[] = [
		// !mark
		{ group: 'File', label: 'File: New', action: newFile },
		{ group: 'File', label: 'File: Open…', shortcut: `${C}O`, action: () => (app.showFileMenu = true) },
		{ group: 'Edit', label: 'Edit: Undo', shortcut: `${C}Z`, action: undo },
		{ group: 'Edit', label: 'Edit: Cut', shortcut: `${C}X`, action: () => void copySelection(true) },
		{ group: 'Edit', label: 'Edit: Find in sheet', shortcut: `${C}F`, action: () => { app.searchAllSheets = false; app.showSearch = true; } },
		{ group: 'Edit', label: 'Edit: Find in all sheets', shortcut: `${C}⇧F`, action: () => { app.searchAllSheets = true; app.showSearch = true; } },
		// !mark
		{ group: 'View', label: 'View: Show grid lines', action: () => (app.showGridLines = !app.showGridLines) },
	];
</script>
```

## !!steps Commands that compute their own arguments

The structural commands are the ones that could not be plain function
references, because what they operate on depends on the selection at the moment
they run.

Reading `getSelectionRect()` **inside** the action rather than when the array is
built is what makes that work — the array is constructed once when the
component mounts, so a captured rectangle would be stale by the time anything
was clicked. Insert-column-left and insert-column-right differ only by whether
they pass the left edge or one past the right.

The two delete commands need a local binding because they use both edges, which
is why they are written as blocks rather than expressions.

```svelte ! CommandPalette.svelte
<script lang="ts">
		// !mark(1:2)
		{ group: 'Insert', label: 'Insert: Column left', action: () => void insertColumn(getSelectionRect().x0) },
		{ group: 'Insert', label: 'Insert: Column right', action: () => void insertColumn(getSelectionRect().x1 + 1) },
		{ group: 'Insert', label: 'Insert: Row above', action: () => void insertRow(getSelectionRect().y0) },
		{ group: 'Insert', label: 'Insert: Row below', action: () => void insertRow(getSelectionRect().y1 + 1) },
		{ group: 'Edit', label: 'Edit: Delete column(s)', action: () => { const s = getSelectionRect(); void deleteColumns(s.x0, s.x1); } },
		{ group: 'Edit', label: 'Edit: Delete row(s)', action: () => { const s = getSelectionRect(); void deleteRows(s.y0, s.y1); } },
</script>
```

## !!steps The one command with its own implementation

`Import: CSV` is the exception that needed real code, because a file picker
cannot be opened programmatically without an `input` element to click.

So one is created, configured and clicked, never entering the document — the
browser shows the dialog regardless. The `accept` attribute filters the picker
to `.csv`, and the handler reads the file as text before handing it to
`importCSVAt` at the current cursor, where the parser in
[gridFile.ts](/docs/src/lib/files/gridFile.ts) takes over.

Nothing removes the element afterwards; it is garbage collected once the
closure is done, since it was never attached to the DOM.

```svelte ! CommandPalette.svelte
<script lang="ts">
	function importCsvViaPicker(): void {
		const input = document.createElement('input');
		input.type = 'file';
		input.accept = '.csv';
		input.onchange = async () => {
			const file = input.files?.[0];
			if (file) await importCSVAt(await file.text(), app.cursorPosition);
		};
		// !mark
		input.click();
	}
</script>
```

## !!steps Closing before acting

`runCommand` closes the palette **first**, then invokes the action, and the
order is deliberate rather than incidental.

Several commands open another dialog — three of them set `showFileMenu`, and
others open go-to, search or the formula reference. Running the action first
and closing afterwards would work for simple commands but risks the close
sequence interfering with the state the action just set. Closing first leaves
the action as the last writer, so whatever it opens stays open.

It also means the palette disappears immediately on Enter, before any slow
action runs, which is what makes the interaction feel responsive.

```svelte ! CommandPalette.svelte
<script lang="ts">
	function runCommand(cmd: Command): void {
		// !mark(1:2)
		close();
		cmd.action();
	}
</script>
```

## !!steps Navigating a list that scrolls

The filter and the two effects match
[CellTypeMenu.svelte](/docs/src/lib/components/CellTypeMenu.svelte) exactly —
focus the search box, reset the selection whenever the query changes.

Navigation differs in two ways, both because this list is long. `Math.max(1,
filtered.length)` guards the modulo against a division by zero when nothing
matches, where the shorter menu could simply return early. And because the list
has a `max-height` and scrolls, moving the selection has to bring the new row
into view — done by finding it through the `data-index` attribute and calling
`scrollIntoView` with `block: 'nearest'`, which scrolls only when the row is
actually outside the viewport rather than centring it on every keystroke.

There is no disabled state to skip here, so the arithmetic is a plain wrap.

```svelte ! CommandPalette.svelte
<script lang="ts">
	function onKeyDown(e: KeyboardEvent): void {
		e.stopPropagation();
		if (e.key === 'Escape') close();
		else if (e.key === 'ArrowDown' || e.key === 'ArrowUp') {
			e.preventDefault();
			const delta = e.key === 'ArrowDown' ? 1 : -1;
			// !mark
			selectedIndex = (selectedIndex + delta + filtered.length) % Math.max(1, filtered.length);
			listEl
				?.querySelector(`[data-index="${selectedIndex}"]`)
				?.scrollIntoView({ block: 'nearest' });
		} else if (e.key === 'Enter') {
			e.preventDefault();
			const cmd = filtered[selectedIndex];
			if (cmd) runCommand(cmd);
		}
	}
</script>
```

## !!steps Rows keyed by label

The list is keyed on `cmd.label`, which doubles as an assertion that labels are
unique — a duplicate would collapse two rows into one keyed entry.

`data-index` exists purely so the keyboard handler can find the selected row in
the DOM without keeping element references. As in the cell type menu, hovering
writes the same `selectedIndex` the arrows write, so mouse and keyboard cannot
disagree about what Enter would run.

The shortcut hint is rendered only when present and pushed to the right by the
row's `space-between`, giving the palette its familiar two-column look without
a grid.

```svelte ! CommandPalette.svelte
			{#each filtered as cmd, i (cmd.label)}
				<button
					class="row"
					class:selected={i === selectedIndex}
					data-index={i}
					onclick={() => runCommand(cmd)}
					onmouseenter={() => (selectedIndex = i)}
				>
					<span>{cmd.label}</span>
					{#if cmd.shortcut}<span class="shortcut">{cmd.shortcut}</span>{/if}
				</button>
			{:else}
				<div class="empty">No matches</div>
			{/each}
```

Rendered by [+page.svelte](/docs/src/routes/+page.svelte) when

Two things worth knowing when reading the list. The shortcut strings are only
partly platform-aware — the Cmd glyph adapts, but `⇧`, `⌥` and the arrow glyphs
are written literally, so a Windows user sees `Ctrl+⇧Z`. And three separate
commands (`File: Open…`, `File: Examples…`, `Help: Example files`) all just open
[FileMenu.svelte](/docs/src/lib/components/FileMenu.svelte) — three doors into
the same dialog, findable under the words someone might actually search for.

The palette is not the source of truth for any shortcut it displays; those are
implemented independently in
[keyboard.ts](/docs/src/lib/grid/keyboard.ts), so a binding changed there would
need updating here too.
